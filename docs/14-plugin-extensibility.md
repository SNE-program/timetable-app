# 插件系统的扩展路线（讨论稿）

这篇不是"已经做完的东西"，而是**下一步该往哪儿加**的讨论：当前插件系统的边界是什么、
每一种扩展要付什么代价、以及哪几种我建议**不做**。

写作时间：v1.9.12 之后。结论先行，论证在后。

---

## 一、现状：一句话说清 v1 插件是什么

**插件是一份 JSON，它只能从宿主已经实现好的功能里挑一个，并给这个功能填参数。
它不能引入任何新代码、不能联网、不能申请宿主还没有的能力。**

这条约束带来的性质值得反复强调，因为后面所有讨论都建立在它上面：

> 装任何插件，都不可能让应用做一件它本来做不到的事。

代价是表达力有限：现在只有两类能力。

| 能力 | 干什么 | 关键字段 |
| --- | --- | --- |
| `export` | 按某种格式导出某一段数据 | `format`(4) × `scope`(6) × `columns`(每范围一组) × `fileName` |
| `command` | 在应用里注册一条命令（可绑快捷键） | `action` 只能指向**本插件自己的** export 能力 |

外加一个权限 `read:timetable`，一份清单要过两轮校验（第一轮逐字段、第二轮交叉引用），
安装时**先 dry-run 再写盘**，存起来之后每次读取**再校验一遍**。

宿主接口版本 `HOST_API_VERSION = 1`：插件写 `apiVersion: 2` 就装不进当前应用 ——
比"装进去之后列错位、导出一张空表"好得多。

## 二、扩展的判据：先问三个问题

任何一条新能力，先过这三个问题；过不了就不做：

1. **宿主要不要新增权限语义？** 例如"联网"是一个全新语义（数据离开设备）。
   只加字段不加权限 = 用户在不知情的情况下多授权了一件事。
2. **用户能不能理解后果？** "导出我的课表"人人懂；"订阅这个 ICS 地址"要懂它会定期联网；
   "执行插件代码"则**没人能懂**（包括写插件的人）。
3. **宿主有没有已经实现好的对应功能？** 如果宿主自己都没有这个功能，
   插件也不能凭空变出来（v1 的根本约束）。扩展的正确姿势是**把宿主已有的功能参数化**。

## 三、候选一：`settingsSchema`（宿主渲染设置表单）

**问题**：插件一旦有参数（导出哪几列、文件名模板、是否含周末），现在只能写死在清单里。
换一个用法就要重新导出一份插件包 —— 而"插件"这个词让人期待它是可配置的。

**做法**：插件声明一个**受限的表单 schema**，宿主用自己的控件渲染，值存进插件私有存储。

~~~json
{
  "type": "settings",
  "id": "prefs",
  "fields": [
    { "key": "includeWeekend", "type": "bool", "label": "包含周末", "default": false },
    { "key": "fileName", "type": "text", "label": "文件名", "maxLength": 40, "default": "我的课表" },
    { "key": "columns", "type": "multi", "label": "导出哪些列",
      "options": ["date", "period", "course", "teacher", "location"], "max": 12 }
  ]
}
~~~

字段类型只开 4 种：`bool` / `text` / `number`（带 min/max/step）/ `multi`（从枚举里多选）。
**没有**自定义校验表达式、没有联动、没有条件显示 —— 一旦有了这些，插件语言就诞生了，
而它一定会长成一门没人会调试的方言。

**代价**：宿主多一个表单渲染器 + 一份按插件 id 分区的 kv（`timetable.pluginData.<id>`）。
这份 kv 要进"本地存储体检"，也要能被一键清掉（现在已有清插件数据的入口）。

**权限**：不需要新权限（数据不出设备）。

## 四、候选二：导入预设（`import`）—— ✅ 已完成（v1.9.14），且**没有加权限**

**问题**：用户手里最常见的脏数据是**学校教务系统导出的表格**，表头五花八门
（"课程名称 / 教学班名称 / 起止节次 / 授课周历"），靠宿主内置的同义词永远追不完。

**落地形状**（与本节最初的设计不同，改的地方在下面）：

~~~json
{
  "type": "import",
  "id": "long-csv",
  "name": "某校教务（一行一个时段）",
  "headers": {
    "name":    ["课程名称", "教学班名称"],
    "teacher": ["任课教师", "授课教师"],
    "day":     ["上课星期"],
    "period":  ["起止节次"],
    "weeks":   ["起止周"],
    "place":   ["上课地点"]
  },
  "headerRow": 2,
  "mode": "long"
}
~~~

字段只有六个，与导入管线里的 `FieldKey` 一一对应 —— **没有新增任何语义**。

### ★ 这张桌子推翻了原计划里的一行：它不需要写权限

原计划给导入配一个新权限 `write:timetable`（当时设想插件提供"列 → 字段"的映射，
并要处理行数上限、ChangeSet 等）。真动手时看清了：插件在这里提供的**只是几个表头写法**，

- 文件是**用户自己选**的；
- 解析、列匹配、预览、入库全是**宿主**在做；
- 入库要**用户点确认**，事后还能撤销。

插件从头到尾没有碰到数据。为这样一件事弹一个写权限，代价不是"多一次点击"，
而是**把权限页变成走过场** —— 当用户发现多数权限请求都无关紧要时，
真正要紧的那几个（读课表、将来的联网）他也会随手点同意。
**权限的价值来自稀缺，不来自数量。** 所以 `import` 与 `settings` 都不需要权限。

**校验拦三种写法**：单字表头（"课"几乎必然抢错列）、带通配符的表头、不认识的字段名 ——
**猜错一列就是整张课表全错**，而课表错了很难手工修回来。
**匹配时预设优先于内置同义词**（预设 200 分档 / 内置 100 分档）：两者都命中时，确定的那个该赢。
**出错要看得出来**：选中预设后当场报命中几个字段，少于 3 个就明说"可能不是这份表"，
而不是照旧显示"已对上"让用户导进一张错课表。

验证：`?importcheck=1`（用一张"别的学校"的样例表 + 一个故意对不上的检查用预设）。

## 五、候选三：界面槽位（`panel` / `card`）—— 建议**先不做**

最容易被提出来的需求是"插件能不能在界面上加一块东西"。我的建议是暂缓，理由不是技术上做不到，
而是这个应用已经有过一次教训：**重复入口本身就是混乱的来源**
（1.9.10 把云备份弹层里的"云端角色"整套界面收掉，就是因为同一件事有两个入口、两套排版、两种说法）。

如果将来一定要做，约束应该写成这样：

- 只开**一个**槽位：设置 → 插件 → 该插件详情页里的一块区域（不外溢到课表页 / 今日页）；
- 插件只能声明**只读的键值展示**（`{label, value}`，最多 6 行），不能放按钮、不能放链接；
- 任何"动作"都必须走 `command`（于是它天然出现在快捷键设置里，可被用户发现、可被禁用）。

换句话说：**能让用户做的动作，全都走命令；界面只负责显示，不负责触发。**
这样插件对界面的侵入上限是"多六行只读文字"，排版不可能被搞坏。

## 六、候选四：事件与提醒（`on` → `notify`）

**问题**：用户会想要"这门课有作业没交就提醒我""考试前一天再提醒一次"。

**做法**：插件声明"监听哪个宿主事件 + 满足什么条件时发一条本地通知"：

~~~json
{
  "type": "rule",
  "id": "ddl-remind",
  "when": { "event": "task.dueSoon", "minutes": 120 },
  "then": { "notify": { "title": "还有 2 小时", "body": "{task.title}" } }
}
~~~

**代价与红线**：

- 通知**只能由宿主发**，插件不能自己弹（否则就是伪造应用通知）；
- 文案模板的占位符必须是**白名单**（`{task.title}`/`{course.name}`/`{time}`），
  不允许表达式 —— 一旦有表达式，插件就能把用户的课表内容拼进任意文本；
- 频率上限由宿主硬编码（每小时最多 N 条），否则用户会被自己装的插件轰炸，
  而责任在应用（通知是应用发的）。

**权限**：`notify` 是新语义，必须单独授权，且授权文案要写清"会发系统通知"。

### ✅ 已完成（v1.9.15），落地时定下的三个数

| 限制 | 值 | 理由 |
| --- | --- | --- |
| 频率上限 | 所有插件合计**每小时 6 条**，按**滑动小时**算 | 装插件 ≠ 同意被刷屏；按整点分桶会出现"59 分发 6 条、01 分又发 6 条"，而用户感受到的打扰是按分钟计的 |
| 文案长度 | 标题 40 / 正文 120 | 通知栏放不下更多 |
| 每插件规则数 | 4 | 安装时直接拒 |

另外两件落地时才想清楚的事：

1. **规则通知并进内置提醒的同一份排程**，不另起发送路径 —— 于是去重（fingerprint + 已发送日志）、
   错过补偿（启动回扫 15 分钟）、滚动排程（只排未来 7 天）全部复用。
   另一条路径 = 另一套去重逻辑 = "偶尔收到两条一样的提醒"。
2. **单独的通知渠道 `plugin-rule`**：不想被插件打扰时只关这一个，上课提醒不受影响。
   让"关掉插件通知"和"关掉全部通知"分开，是插件功能能被长期接受的前提。
   渠道不在 `CHANNELS` 里的话 Android 会**静默丢弃**通知，所以自检里专门核对了它。

事件只开三种：`task.dueSoon` / `class.before` / `daily.at`。`daily.at` 那天一节课都没有时不发 ——
用户装这类规则是为了"今天有什么"，不是说早安。

## 七、候选五：联网（ICS 订阅 / 课表同步）—— 最后做，且必须"看得见"

**问题**：真实需求第一名是"自动同步学校课表"。

**为什么危险**：这是唯一会让**数据离开设备**的能力。即使只发一个 GET，
URL 里也可能带上标识（学号、token）。而"无广告无追踪"的承诺是建立在这个应用不发任何请求之上的。

**如果要做，形状应该是**：

- 权限名必须直白：`net:fetch`，安装时用一句话说清"它会访问你填写的网址，网址和返回内容不会是别的用途"；
- **只允许用户填的地址**（插件不能自带 URL 模板去拼，否则就是一个把课表发出去的后门）；
- 域名白名单由用户确认（第一次访问某个域名时弹一次，记在设置里，可撤销、可查看访问记录）；
- 抓回来的内容只走**声明式导入映射**（候选二），不引入第二种解析路径。

这条我建议排在最后：它的收益最大，但只有在"导入映射 + 写权限 + 权限界面"都成熟之后，
它才是加法而不是一个新的风险面。

## 八、候选六：执行插件代码 —— 明确不做（至少现在）

理由在 `src/plugins/types.ts` 顶部已经写过，这里补一条**新的**：

前四个候选加在一起，插件能做的事已经覆盖了绝大多数真实需求（导入、导出、设置、提醒）。
而"能跑代码"真正多出来的是**宿主没想到的事** —— 也正因为想不到，宿主没法为它设计权限、
没法给它做界面、更没法在出问题时告诉用户是谁干的。

真要做，正确形状是**独立沙箱**（单独的 WebView / Worker + 消息协议 + 白名单能力），
那是另一个量级的工程，且会让"产物里没有第三方运行时"这条可验证的性质消失。
**结论：不作计划。** 如果哪天做，它会是一次独立的大版本，而不是插件系统的一次迭代。

## 九、建议的顺序与每步的验收

| 顺序 | 能力 | 新增权限 | 宿主新增工作量 | 验收判据（可测） |
| --- | --- | --- | --- | --- |
| 1 ✅ **已完成（v1.9.13）** | `settingsSchema` + 插件 kv | 无 | 表单渲染器 + 分区存储 + 体检/清理 | `?plugcheck=1` 全绿：改设置后导出结果真的变了、清数据后回到默认值 |
| 2 ✅ **已完成（v1.9.14）** | `import` 导入预设（表头写法） | **无**（原计划写的是 `write:timetable`，落地时论证掉了 —— 见第四节） | 表头同义词 + 预设优先匹配 + 命中数提示 | `?importcheck=1` 全绿：切换预设后表头行/命中数跟着变，选错时有提示 |
| 3 ❌ **不做（v1.9.15 决定）** | 只读 `panel` 槽位 | 无 | — | 动手前问了一句"它解决谁的什么问题"，答案是没人：插件能显示的东西用户在自己的课表里都看得到，多一块自留地只会让设置页更长 |
| 4 ✅ **已完成（v1.9.15）** | `rule` → 宿主发通知 | `notify` | 三种事件 + 模板白名单 + 频率上限 + 独立渠道 | `?rulecheck=1` 全绿：漏出的占位符 0、渠道已建 yes、最忙一小时 1/6；撤权限后 `activeRules()` 立刻为空 |
| 5 | `net:fetch` | `net:fetch` | 域名白名单 + 访问记录 + 只在用户确认后请求 | 未确认域名时请求不发生（可抓包/看日志验证） |

每一步都要配套三件事，缺一不可：

1. **`HOST_API_VERSION` +1**，并且旧插件（`apiVersion` 低）仍然照常工作 —— 这条要写成测试；
2. **权限界面**：新权限必须在安装确认页里有一句人话解释（现在的 `PERMISSION_LABEL` 就是这个位置）；
3. **一条能失败的检查**：例如"撤销权限后能力立刻失效""清掉插件数据后回到默认值"。
   一个永远通过的检查等于没有检查。

## 十、三条不变量（以后加任何能力都要守住）

1. **插件是数据，不是代码**：宿主不 eval、不 `import()`、不执行任何来自插件的字符串。
2. **装插件不能让应用做新的事**：新能力的实现必须先存在于宿主里，插件只是参数。
3. **可撤销**：任何插件造成的数据变化都要走 ChangeSet；任何插件带来的状态都要能被一键清掉。
