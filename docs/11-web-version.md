# 10 网页版：能力边界、发布与验证

> 记录时间：v1.4.0。这份文档回答三个问题：网页版**能做什么**、**怎么发**、**凭什么说它是对的**。

## 1. 为什么要做网页版

Android 版把该做的都做了，但分享门槛高：要传 APK、要允许未知来源、iOS 与电脑上根本装不了。
同学之间传播一份课表的成本，比功能本身更影响它有没有用。网页版把这一步压到「点开一个链接」。

约束没有变：**仍然不联网、不注册、不上传**。网页版不是"云版本"，它只是换了一个宿主 —— 
数据依然在用户自己的设备上（浏览器本地存储），打包出来的静态文件里没有任何一处会发起网络请求。

## 2. 迁移范围：哪些能搬，哪些搬不动

判据只有一条：**这项能力是不是依赖只有原生壳才有的系统能力**。

### 直接可用（占绝大多数）

| 模块 | 说明 |
| --- | --- |
| 时间引擎、周次、调停补课、无限时间轴 | 纯计算，与平台无关 |
| 本周 / 今日 / 任务 / 出勤 / 搜索 / 课程详情 | 纯界面 |
| Excel / CSV 导入 | 自己写的 ZIP + `DecompressionStream` 解 xlsx，本来就没用原生能力 |
| ICS、CSV、Markdown、长图、JSON、主题包、角色包、分享码 | 导出改走浏览器下载（`webDownload()`）|
| 外观 DIY、角色（含视频抽帧、走动、翻面、快捷菜单） | Canvas 与 CSS 动画，与平台无关 |
| 声明式插件、说明书、更新日志 | 纯数据与文案 |

### 换成网页版的实现

| 原（Android） | 网页版 |
| --- | --- |
| `CapacitorNotifier`：系统闹钟，息屏 / 关应用 / 重启后仍有效 | `WebNotifier`：页面内 `setTimeout` + 系统通知，**页面保持打开时**准时 |
| 保存文件走 Filesystem + Share | 浏览器下载（`Blob` + `a.download`），行为差异写进说明书 |
| 资产存 SQLite（配额宽松） | 存 localStorage，与结构化数据共用约 5 MB 配额 |

### 删掉（面板整块换成实话）

- **桌面小组件**（2×2 / 4×2）：由系统进程绘制在桌面上，浏览器没有对应能力。`WidgetPanel` 在网页版整个换成说明块，并在构建注入了仓库地址时给出 Android 版入口。
- **电池优化白名单 / 自启动 / 精确闹钟授权**：Android 专有权限，网页版没有可点的系统页面。`SettingsView` 里的「后台提醒可靠性」整块换成 `WebReminderPanel`。
- **8 项提醒可靠性检查**：息屏、强停、重启、改时间、换时区、省电模式在浏览器里没有意义。`WEB_TESTS` 换成 3 项，其中一项本身就是"关掉页面就不会响"。

## 3. 文案策略：宁可少说，不说错

这一版最难的不是删代码，是**不让网页版继承 Android 的承诺**。"息屏也会提醒""关掉应用照样响"这类句子，
在网页版是假的 —— 用户信了，就会在某天早上错过一节课，然后卸载。所以：

1. **首次启动的隐私说明**最后一条按平台换写法：Android 是「提醒交给系统闹钟」，网页版是「提醒需要页面保持打开」，并直接给出"要关掉也响就装 Android 版"；
2. **设置页**保留原位置，把 Android 的电池区块换成「网页版的提醒边界」，写清三条限制（页面要开着、后台标签页会被限速、数据不跨设备）；
3. **说明书**按平台分支：提醒章节的"必须放行的四项"在网页版变成"四条边界"，FAQ 里"到点没有提醒""点导出之后文件在哪""桌面小组件不刷新""换手机怎么迁移"都各有一份网页版答案；
4. **更新日志**顶部加一条平台提示：历史条目里「交给系统闹钟」「桌面小组件」「电池优化」属于 Android 版 —— 记录不改写，但读者要知道自己在看什么。

实现上只有一个判据：`isNativePlatform()`（来自 `src/platform/nativeBridge.ts`）。
分支散落在 `Welcome.tsx` / `SettingsView.tsx` / `WidgetPanel.tsx` / `DeviceCheckPanel.tsx` / `WebReminderPanel.tsx` / `ManualView.tsx` / `ChangelogSheet.tsx`，
没有第二处判断标准（比如 UA 嗅探），避免出现"看似网页版、其实走 Android 分支"的第三种状态。

## 4. 发布

```
推送 main  →  GitHub Actions（.github/workflows/web.yml）
              ├─ npm ci
              ├─ npm test        # 单测不过就不发
              ├─ npm run build   # base: './'，产物可直接放子路径
              └─ deploy-pages    # 发布 dist/
```

一次性准备：仓库 **Settings → Pages → Source** 选 **GitHub Actions**。

**为什么用相对路径**：项目页地址是 `https://<user>.github.io/<repo>/`，绝对路径 `/assets/…` 会指到域名根目录，整站白屏；
相对路径在子路径、自定义域名、以及 Capacitor 的 `https://localhost/` 下都成立，所以两个平台共用一份构建产物。

**Android 下载入口**：构建时把 `GITHUB_REPOSITORY` 注入成 `__REPO_URL__`（见 `vite.config.ts` 与 `src/app/meta.ts`）。
本地构建没有这个环境变量，入口自动隐藏 —— 宁可少一个按钮，也不要一个猜出来的死链。
APK 请放在仓库 **Releases**，网页版的入口指向 `/releases/latest`。

## 5. 存储：说清 5 MB 这件事

Android 版把图片资产放进 SQLite，正是为了绕开 localStorage 约 5 MB 的配额；
网页版没有这个后端，`initStorage()` 会落到 `localStorage`，图片与结构化数据共用同一份配额。

所以网页版的说明书「数据与存储」章节写的是：放一两张小图没问题，别把整本相册塞进来；
清除站点数据、换浏览器、无痕窗口都会丢数据，换设备前先导出 JSON。
**后续路线**：把资产后端换成 IndexedDB（配额按磁盘比例给，通常几百 MB 起）。
这件事值得做，但要连同"旧数据迁移 + 配额耗尽时的降级"一起做，所以没有塞进这一版。

PWA（manifest + service worker）同样**刻意留到后面**：
离线缓存一旦铺上，快速发版时用户会拿到旧版本，而"版本对不上"是这个项目里最难查的一类问题。
先把版本发稳，再谈安装到桌面。

## 6. 怎么验证的（无头浏览器 + 自检回传）

网页版和 Android 共用同一套自检（`src/app/diagnostics.ts`，`?diag=1`），另外补了一个能看"渲染出来到底是哪一支文案"的口子：

| 手段 | 看什么 |
| --- | --- |
| `?diag=1&w=320,360,390` | 三个宽度下的横向溢出、触控尺寸、字号、断行、标签栏是否出框、React 有没有整树崩掉 |
| `PLATFORM` 指标 | 产物自己认为跑在哪个平台（网页版必须是 `web`） |
| `?diag=1&text=<选择器>` | 把匹配元素的**渲染后文字**回传 —— 平台分支只能这样查 |
| `?report=端口` | 1×1 图片信标把上面这些发回本机（只有带这个参数才会联网） |

这一版实际跑过的检查（在本机把 `dist/` 挂到 `/repo/` 前缀下模拟 Pages 子路径）：

- 子路径下资源全部 200，无 404；
- 320 / 360 / 390 三个宽度：`OVERFLOW 0`、`SMALL_TAP 0`、`MARKDOWN 0`、`ROOT ok`、标签栏 5 项全在框内；
- 文案抽查（都是真实渲染结果）：首次启动 4 条说明、设置页各面板、说明书提醒 / 存储 / FAQ / 版本四章、更新日志顶部提示；
- 检查清单在网页版确实是 **3 项**（Android 是 8 项）；
- 注入 `VITE_REPO_URL` 后网页版出现 3 个 Android 下载入口；不注入时 0 个。

## 7. 还没做的

- **IndexedDB 资产后端**：见第 5 节，配额是网页版最实际的痛点；
- **PWA / 离线**：等版本节奏稳定；
- **真正的后台提醒**：浏览器不给网页这个机会（Web Push 需要服务器，与"不联网"的底线冲突），所以不做，只在界面上说清楚；
- **多设备同步**：同样与底线冲突，替代方案始终是"导出 JSON 带走"。
