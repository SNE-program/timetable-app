## 一、手机端适配

### 1. 先解决"怎么量"的问题

我看不到截图，所以先写了一个**布局自检工具**（`src/app/diagnostics.ts`，加 `?diag=1` 打开），
把当前视口下的布局问题量化输出：横向溢出元素、触控目标尺寸、字号、文字截断、关键元素尺寸。

**踩到的坑**：无头浏览器在 Windows 上有**最小窗口宽度限制（约 504px）**，
`--window-size=320,640` 出来的视口仍然是 504 宽 —— 根本测不了窄屏。

试过只约束容器宽度，但**骗不过媒体查询**（媒体查询看的是真实视口），
所以那个版本的测量结果是错的（`--axis-w` 明明写了窄屏值却没生效）。

最终方案：**用 iframe**。iframe 的视口就是它的尺寸，媒体查询会正确生效：

~~~ts
const frame = document.createElement('iframe');
frame.style.width = w + 'px';
frame.style.height = Math.round(w * 2.05) + 'px';
// 在 frame.contentDocument 里测量
~~~

### 2. 实测出来的问题

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 横向溢出元素 | **40** | **0** |
| 触控目标 < 44px | **25** | 1（只剩日期输入框） |
| 字号 < 11px | **70** | 1 |
| 文字被截断 | **33** | 4 |
| 课程卡宽度（360px 屏） | 37px | 44px（7 天）/ 约 58px（5 天） |
| 顶栏高度 | 106px | 101px（矮屏自动压到更扁） |

### 3. 具体改了什么

**安全区（刘海屏 / 手势条）**
```
--sat / --sab / --sal / --sar  ← env(safe-area-inset-*)
```
顶栏、标签栏、悬浮按钮、弹层、Toast 全部改用这四个变量，横屏时左右刘海也不会压住内容。

**触控目标：视觉紧凑 + 命中区外扩**
不靠把控件做大，而是用伪元素把可点区域撑到 44px：

~~~css
.icon-btn { width: 36px; height: 36px; }
.icon-btn::after { content: ""; position: absolute; inset: -4px; }  /* 实际 44x44 */
~~~

周次胶囊用 `::before` 外扩（`::after` 被"本周"小圆点占用了）。

**字号下限**
节次时间 9px → 11px，星期标签 9.5px → 11px，节次序号 10px → 11px，
课程卡 10.5px → 11px，微小标签统一提到 11px。

**窄屏媒体查询**
| 断点 | 动作 |
| --- | --- |
| ≤ 430px | 隐藏卡片里的教师名（让位给课程名和教室），课程名允许 4 行 |
| ≤ 380px | 节次轴 42→30px，边距 14→10px，网格间隙 2px，隐藏重复的周次文字 |
| 矮屏（≤700px 高） | 压扁顶栏、隐藏学期副标题 |
| 横屏（≤560px 高） | 行高 68→54px，标签栏压扁，悬浮按钮缩小 |
| ≥ 700px | 内容居中约束在 520px，不拉成一条 |

**触屏细节**
- `touch-action: manipulation`：去掉双击缩放带来的 300ms 延迟与误触
- `@media (hover: none)`：关掉悬停效果，避免手指点完后样式"粘住"
- `prefers-reduced-motion`：尊重系统的"减弱动态效果"
- `overscroll-behavior: none`：去掉橡皮筋抖动
- `100dvh` 保留 `100vh` 兜底

### 4. 根本矛盾与它的解法

**360px 屏上排 7 列，每列只有 44px。** 这是几何问题，没有魔法能绕过。
硬塞的结果就是课程名挤成两三个字、教室名被截断。

所以加了 **「每周显示几天」** 选项（5 / 6 / 7）：

| 显示天数 | 360px 屏每列宽度 | 效果 |
| --- | --- | --- |
| 7 天 | 44px | 课程名约 3 个字 |
| 6 天 | 51px | 约 4 个字 |
| 5 天 | 58px | **课程名基本能完整显示** |

位置：外观 DIY → 文字与排版 → 每周显示几天。默认仍是 7 天（不能悄悄藏起周末的课）。

课表里长按任意课程卡 500ms，直接打开调课面板，不用先点进课程详情再找。

# 追加修复（v0.6.2）

## 一、背景图片不显示

### 根因

`src/theme/apply.ts` 里只处理了**预设壁纸**：

~~~ts
if (theme.wallpaper.kind === 'preset' && theme.wallpaper.presetId) {
  vars['--wp-image'] = src ? 'url("' + src + '")' : 'none';
}
// kind === 'custom'（用户自己上传的图片）→ 什么都不做，
// 而 resolveTokens 里默认写的就是 'none'
~~~

所以**自定义上传的壁纸从来没有被应用过** —— 预览里选了、导出的主题包里也带着图片，
但主界面上永远是纯色背景。预设壁纸（极光/霓虹/纸纹…）是正常的。

### 顺带修掉的隐患

即使把自定义图片塞进 `--wp-image` 变量，也不可靠：
自定义壁纸是几百 KB 的 base64，作为 CSS 自定义属性再被 `var()` 引用，
长度和转义都容易踩坑。

现在改成**直接写 `.wallpaper` 元素的 `background-image`**，绕开变量这一层：

~~~ts
const el = document.querySelector('.wallpaper');
el.style.backgroundImage = image;   // 'none' 时同时 display:none，省掉一次合成
~~~

并且主题切换时用 `requestAnimationFrame` 补一次应用，避免首屏元素还没挂载。

### 验证

| 情况 | 结果 |
| --- | --- |
| 默认主题（工作台，本来就没有壁纸） | 隐藏，符合预期 |
| 预设壁纸 | 有背景图 ✓ |
| 自定义上传的图片 | **有背景图 ✓（修复前是坏的）** |

> 提醒：默认主题「工作台」刻意是干净的纯色，没有壁纸。
> 想要背景图请到 外观 DIY → 背景，选一张内置壁纸或者上传自己的图。

## 二、课程时间（第几节几点）自己设定

功能其实一直在 **设置 → 作息与节次** 里（切换方案、逐节改时间、复制新增），
但入口藏得太深，这次做了三件事：

### 1. 接到节次轴上

周视图左侧的**节次轴现在可以直接点**（顶部还有个 ⚙ 提示），点开就是作息设置。
这是最符合直觉的位置 —— 用户看到"第 1 节 08:00"，想改就会去点它。

### 2. 改动即时生效

原来是「改完 → 点右上角保存」。手机上很容易改完直接关掉面板，改动全丢，
用户会以为"这个功能不能用"。现在**每一次改动立刻落库并重排课表**，
右上角按钮从「保存」改成「完成」。

### 3. 顺手修掉一个示例数据的 bug

示例里的「冬季作息」是坏的 —— 结束时间是 `'0' + (9 + Math.floor(i/2))` 拼出来的垃圾
（会得到 "010" 这种），而且所有开始时间都是同一个值。现在改成正确实现：
**上午整体推后半小时，晚自习不变**。

验证：夏季 08:00 开始，冬季 08:30 开始，同一门课的时间跟着平移。

# 追加修复（v0.6.3）

## 一、背景图片"被拉伸"

### 先说结论：不是拉伸，是**放大裁切**

CSS 用的是 `background-size: cover`，它保持宽高比、裁掉多余部分，**不会变形**。
你看到的问题来自两件事叠加：

1. **手机是竖长屏，横图要放大好几倍才能铺满** —— 一张 1600×900 的图铺到 360×780 的屏幕上，
   要放大到 360 × (900→2000+) 的尺寸，等于只看得到中间一小块，剩下的全被裁掉。
   放大的部分自然糊，看起来就像"被拉扁了"。
2. **额外还有一个 6% 的放大**（`transform: scale(1.06)`），那是早期为了遮住模糊边缘加的，
   现在只在**开了模糊**的时候才启用。

### 修复

**1. 导入时可以自己剪裁（你要的功能）**

选完图片不再直接应用，而是打开一个剪裁面板：

- 画布比例 = **你手机屏幕的比例**，所见即所得 —— 框出来的就是主界面上的效果
- 拖动调整位置，滑块缩放（1×～4×）
- 有三分线辅助构图
- 输出 1920 长边的成品图，**比例已经和屏幕一致**，主界面上不会再被二次裁切
- 原始图保留在本机，随时可以点「重新剪裁」重来（原图不会写进主题包，避免体积翻倍）

**2. 新增「显示方式」三选一**

| 方式 | 效果 | 适合 |
| --- | --- | --- |
| **填满** | 铺满屏幕，裁掉多余 | 竖图、想铺满的图 |
| **完整** | 整张图都显示，两边留底色 | 横图、不想裁掉内容的图 |
| **平铺** | 小图重复铺开 | 纹理、图案 |

**3. 只在真需要时才放大**

`scale(1.06)` 改成仅当「背景模糊 > 0」时启用 —— 模糊会让边缘透出底色，才需要放大遮住。

# 防误触设计（v0.7.1）

## 一、外观锁定

**默认锁上。** 进「外观」页是只读状态，改不了任何东西。

| 行为 | 说明 |
| --- | --- |
| 锁定状态下 | 所有控件点不动（pointer-events 置为 none），面板整体降到 62% 透明度 |
| **仍然可以** | 上下滑动浏览所有主题和选项 —— 锁的是「改」，不是「看」 |
| 解锁 | 顶部固定条上的「解锁」按钮，一次点击即可 |
| **自动锁回** | ① 离开外观页时 ② 解锁后 3 分钟没有任何操作 |
| 记住状态 | 存在本机偏好里，重启 App 依然是锁的 |

顶部那条锁定栏是 sticky 的，滑到哪儿都看得到当前状态。

> 设计取舍：这是**防手滑**，不是防别人。所以不需要密码，解锁只要一下点击；
> 但「解锁」这个动作必须是主动的，而且会很快自动收回。

## 二、其他防误触改进

### 1. 周视图滑动：不再从课程卡上起手

以前在课程卡上横向拖动也会翻周 —— 但用户多半是想点课程卡，结果课表翻了。
现在**从课程卡、按钮、输入框、标签上开始的拖动一律不翻周**，只有从空白处滑动才翻。

同时滑动阈值从 55px 提到 **72px**，纵向容差从 45px 收到 40px。

### 2. 长按调课：加了两道闸

- 长按时间 500ms → **600ms**
- **手指移动超过 10px 立即取消** —— 以前滚动课表时如果手指停在卡片上超过半秒，会莫名其妙弹出调课面板

### 3. 表单：未保存提醒 + 防重复提交

- 课程编辑器关掉前如果有没保存的改动，会先问一句「有还没保存的修改，确定要放弃吗？」
- 保存按钮点击后立刻禁用并显示「保存中…」，连点两下不会存两条

### 4. 危险操作统一走一个开关

删除课程、清空课表、载入示例、导入覆盖、删除任务 —— 全部走同一个 confirmDanger()，
可以在 **设置 → 操作保护** 里整体关掉。

而所有这类操作**都支持「撤销」**：操作后 Toast 上会出现撤销按钮，6 秒内一键还原。
确认弹窗和撤销是两道独立的防线。

### 5. 周次条的步进按钮

两个翻页箭头和周次胶囊之间加了 4px 间距，并把步进按钮的边框加深，
避免想点第 7 周结果点到了翻页。

# 自检报错定位（v0.7.4）

## 报错：Cannot read properties of undefined (reading 'load')

**这是我代码里的一个低级但致命的 bug。**`probe()` 里几个步骤函数是这样调用的：

~~~ts
await run('加载通知插件', async function () {
  const ln = await this.load();   // ← this 是 undefined
});
~~~

`run(name, fn)` 内部是 `await fn()` —— **不带接收者调用**。
ES 模块默认是严格模式，所以回调里的 `this` 是 `undefined`，
`this.load()` 直接抛错。

受影响的 4 个步骤（加载插件 / 查权限 / 查排程 / 查精确闹钟）**全部第一时间就失败了**，
所以自检看起来「什么也没跑出来」。

修法：在 `probe()` 开头存一份 `const self = this;`，回调里统一用 `self`。
（其余方法里的 `this` 都在正常的方法体内，不受影响，已逐一核对）

**有意思的是**：这个报错反而是个好消息 —— 它只存在于 v0.7.3 的自检代码里，
说明**新包确实装上并在运行了**，之前怀疑的「页面缓存了旧代码」可以排除。

# 提醒全线卡死的根因（v0.8.3）

你发来的诊断信息里最刺眼的一行是这个对比：

| 步骤 | 结果 | 耗时 |
| --- | --- | --- |
| 检测运行环境 | 通过 | 4 ms |
| 读取系统版本 | 通过 | 4 ms |
| **加载通知模块** | **超时** | **12001 ms** |
| **加载文件模块** | **超时** | **12001 ms** |
| **加载分享模块** | **超时** | **12001 ms** |

纯 JS 的步骤 4 毫秒就过，**只要碰 Capacitor 插件的步骤全部卡死在同一个数字上**。
这说明插件本身、权限、通道全都没问题——问题出在「把插件模块取到手」这一步。

## 一、根因：Vite 的动态导入预加载在 WebView 里永不回话

原来的代码为了「插件加载失败也不影响首屏」写成：

```ts
const mod = await withTimeout(import('@capacitor/local-notifications'), 10000, '...');
```

动态 `import()` 会让 Vite 把插件切成独立 chunk，并包一层预加载助手：

```js
__vitePreload(() => import('./web-xxx.js'), [依赖列表])
```

这个助手的实现是：先往 `<head>` 里插 `<link rel="modulepreload">`，
然后 **等到它的 `load` 事件或 `error` 事件触发** 才继续。

在 Capacitor 的 Android WebView（Chrome/138）里，这类 link 的 `load`
**既不触发也不报错**，于是这个 Promise 永远 pending。外面包几层
`withTimeout` 都没用——它连 reject 的机会都没有，只能等超时器把它砍掉，
所以你看到的永远是整整齐齐的 12001 ms。

## 二、修法：把动态导入全部改成静态导入

三个文件里的运行时动态导入全部消灭：

| 文件 | 原来 | 现在 |
| --- | --- | --- |
| `src/platform/capacitorNotifier.ts` | `await import('@capacitor/local-notifications')` | 顶部 `import { LocalNotifications } from ...` |
| `src/platform/shareImage.ts` | `await import('@capacitor/filesystem')` / `'@capacitor/share'` | 顶部静态 import |
| `src/app/diagnostics.ts` | `await import('./store')` 等 | 顶部静态 import |

插件进主包后，「取模块」这个动作在运行期**根本不存在**了，没有 import 就没有可卡的地方。

构建配置同时加了两道保险：

```ts
build: {
  modulePreload: false,          // 不再生成 modulepreload
  rollupOptions: { output: { manualChunks: undefined } },  // 不再任意切块
}
```

产物验证：主包里 `__vitePreload` 出现 **0 次**，`dist/index.html` 里
modulepreload 链接 **0 个**。

## 三、剩下的 3 个 web-*.js 为什么不影响手机

打包后仍会看到 `web-*.js` 三个小文件，这是 Capacitor 自己的**网页兜底实现**
（浏览器里跑才用得上）。它由 `registerPlugin` 惰性加载：

```js
if (!jsImplementation && platform in jsImplementations) { ... await jsImplementations[platform]() }
```

安卓上 `platform === 'android'`，而注册表里只有 `{ web: ... }`，
`'android' in { web: ... }` 为 **false**，这段代码在手机上永远不执行，
那 3 个文件永远不会被 import。所以它们既占不了体积也卡不住进程。

## 四、顺手修掉的构建硬错误

`vite build` 之前其实一直在**静默失败**（所以 `dist/assets` 是 0 个文件，
你装到的还是旧包）。rolldown 报的是：

```
Imports are immutable in JavaScript. To modify the value of this import...
   migrateNotes = [];
```

`src/app/store.ts` 里 `export let migrateNotes` 被 `App.tsx` 直接赋值，

## 五、顺手修掉的一个真机必崩 bug：ICS 导出

在 `src/core/ics.ts` 里，RFC5545 要求的「每行不超过 75 个八位组」折行函数
用的是 **`Buffer`**：

```ts
const bytes = Buffer.from(line, 'utf8');   // ← Node 专有全局
```

单测跑在 Node 里，`Buffer` 当然存在，所以 115 个测试一路绿灯；
但真机 WebView 里根本没有 `Buffer`，**ICS 导出一点就 ReferenceError**。
这就是「测试全过、装机就崩」的典型盲区。

改成 `TextEncoder`（浏览器和 Node 都有），并补了一条**能把真机条件搬进测试**的用例：
把 `globalThis.Buffer` 临时置为 `undefined` 再导出一次。
这条用例在修复前必然失败，修复后通过 —— 以后不会再有人把它改回去。

同时扫了一遍全部前端代码，确认再没有 `process` / `require` / `__dirname` /
`global` / `Buffer` 这类 Node 专有全局混进来。

# v0.8.3 没修好 —— 真正的原因（v0.8.4）

装上 v0.8.3 之后，自检**依旧**是整整齐齐的 12001ms。也就是说我上一轮的判断
只对了一半：**动态 import 确实是元凶，但我认错了是哪一次、也没找到触发条件。**

## 一、把用户装的包拆开看

我把 v0.8.2 的 APK 解开，先弄清它**实际加载**的是哪个 bundle
（那个包里有 50 份 `index-*.js`，随便挑一个必然看错）：

```
assets/public/index.html  →  /assets/index-C8G5z-GG.js
```

然后在这个 bundle 里找到 `load()` 的真实代码：

```js
async load(){
  if(this.mod) return this.mod;
  if(this.loadError) throw Error(this.loadError);
  try{
    let e = await zr(Vt(() => import(`./esm-xunr1R7u.js`), []), Br, `加载通知插件`);
    ...
  }
}
```

`Vt` 就是被压缩改名后的 `__vitePreload`（所以之前搜 `__vitePreload` 字面量
当然是 0 次，我被这个误导了）。**挂起的就是这次 `import()`。**

## 二、那个 chunk 里写着答案

`esm-xunr1R7u.js` 只有 588 字节，全文如下：

```js
const __vite__mapDeps=(i,m=__vite__mapDeps,d=(m.f||(m.f=[
  "assets/web-UUl_LOre.js","assets/index-C8G5z-GG.js","assets/index-CPRSA2-2.css"])))=>i.map(i=>d[i]);

import{i as e,t}from"./index-C8G5z-GG.js";

var r = e(`LocalNotifications`, {
  web: () => t(() => import(`./web-UUl_LOre.js`), __vite__mapDeps([0,1,2]))
});
export { r as LocalNotifications };
```

`e` = `registerPlugin`，`t` = `__vitePreload`。也就是说：
**打包器把 `@capacitor/local-notifications` 切成了一个独立 chunk，而这个 chunk
的第一件事就是回头去 import 主包和网页兜底。**

## 三、为什么它会挂

回看 Capacitor 的 `registerPlugin`：

```js
const createPluginMethodWrapper = (prop) => {
  const wrapper = (...args) => {
    const p = loadPluginImplementation().then((impl) => { ... });   // ← 每次取方法都先跑这个
    ...
  };
};
```

而 `loadPluginImplementation` 是：

```js
if (!jsImplementation && platform in jsImplementations) { ... await jsImplementations[platform]() }
```

只要 `platform` 被判成 `'web'`，它就会**去 import 网页兜底实现**（`web-*.js`）。
这条路径一旦走上，就是一个我们控制不了、也无法超时的动态 import。
换句话说：**这个第三方插件的代理层里埋着一条随时可能被触发的动态 import，
而它在 Capacitor 的 WebView 里会永远挂着。**

我上一轮只把"我们自己写的 `import()`"改成了静态导入 —— 那一步是对的，
但没触及代理层内部的那一条，所以病根还在。

## 四、v0.8.4：把代理层整个绕开

新增 `src/platform/nativeBridge.ts`，直接调 `cap.nativePromise`：

```ts
export function nativeCall<T>(plugin: string, method: string, options?: unknown): Promise<T> {
  const cap = getCap();
  if (!cap) return Promise.reject(new Error('原生桥不可用：没有 window.Capacitor'));
  if (typeof cap.nativePromise === 'function') {
    return cap.nativePromise(plugin, method, options || {}) as Promise<T>;
  }
  ...
}
```

这不等于"绕过插件"—— `nativePromise` 走的就是代理层最终要做的那一件事
（`toNative` → `androidBridge.postMessage`），**只是少了一次模块加载**。

三个插件的 JS 包因此可以整个不要：

| 文件 | 原来 | 现在 |
| --- | --- | --- |
| `capacitorNotifier.ts` | `import { LocalNotifications } from '@capacitor/local-notifications'` | `nativeCall('LocalNotifications', 'checkPermissions', …)` |
| `shareImage.ts` | `Filesystem` / `Share` 包 | `nativeCall('Filesystem'/'Share', …)` |
| `reliability.ts` | `registerPlugin('Reliability')` | `nativeCall('Reliability', …)` |

原生侧完全不受影响 —— `capacitor.plugins.json` 里三个插件照常注册，
`@capacitor/android` 也照常把它们编进 APK，只是 JS 侧不再需要那几个包。

# 图标底色 + 一轮优化（v0.8.5）

## 一、图标底色：白 → `#2F3237`

你说白色有点奇怪，是对的，而且原因能量出来。我把源图 `123jie.png` 拆开统计：

| 指标 | 实测 |
| --- | --- |
| 全透明像素 | **0%** |
| 半透明像素（alpha 217） | **91%** |
| 外侧 3% 的平均色 | **`rgb(106,107,115)` ≈ `#6A6B73`** |

两条结论：

1. **源图外圈本身就是中性灰**，而且九成像素带 85% 的半透明 —— 底色会直接从画面里透出来。
   白底等于在一块灰边图案外面又套了一圈白环，所以看着别扭。
2. 自适应图标 = **底色铺满 + 图案缩到 70% 居中**，那圈留白全是底色。
   底色和图案边缘越接近，整块砖越完整。

改成同色系的深灰 `#2F3237` 之后两者贴合。想再调只改 `.gen-icons.cjs` 里的
`const BG = [47, 50, 55];` 一行。

顺便修掉一个之前没注意到的问题：**方形/圆形图标（`ic_launcher.png` / `ic_launcher_round.png`）
是源图直接缩放的，那 91% 的半透明一直没被压平** —— 在老版本桌面上会直接透出壁纸。
现在统一先 `flatten()` 压到实色底上，观感可控了。

另外生成了一张底色候选对照图 `shots/icon-bg-options.png`，六个候选色并排，
从左到右是：`#FFFFFF` `#E8E9EB` `#6A6B73` `#3A3D42` `#2F3237` `#1F2126`。
想换一个直接说序号就行。

## 二、这轮找到的问题

### 1. 切换任何偏好都会把全部通知重排一遍（最值钱的一个）

`App.tsx` 里同步提醒的副作用依赖的是**整个 `prefs` 对象``**：

```tsx
React.useEffect(function () { syncReminders(data, prefs) ... }, [data, prefs]);
```

而 `prefs` 里除了 `reminderOffsets` / `dailyBrief` / `briefHour` 之外，还装着
`studioLocked` 和 `confirmDestructive`。其中 **`studioLocked` 会在离开外观页时自动打开**
（`setTab` 里），闲置 3 分钟也会自动打开（`ThemeStudio` 的定时器）。

于是：**每次从「外观」切走一个标签页，都要「取消全部通知 → 重新排一遍」**。
不只是白跑几趟原生调用 —— `replaceAll` 是先 `cancelAll` 再 `schedule`，
那几百毫秒里所有提醒是真的处于已取消状态。

改法是把依赖拆开，只依赖真正影响提醒的字段：

```tsx
const reminderOffsetsKey = s.prefs.reminderOffsets.join(',');
React.useEffect(function () { ... }, [s.data, reminderOffsetsKey, dailyBrief, briefHour]);
```

### 2. 学期「不设结束」时，右滑翻周是坏的

`ui/WeekView.tsx` 的滑动手势里写的是：

```ts
if (next >= 1 && next <= data.term.totalWeeks) setWeek(next);
```

`totalWeeks` 是**可选**的（学期留空就是"不设结束"），而 `n <= undefined` 在 JS 里
恒为 `false`。所以只要把总周数清空，**右滑就再也翻不动了**。

这跟整个设计是矛盾的：`clampWeek` 只按 `[1, MAX_WEEK]` 夹，
`App.tsx` 的周次条也早就按"不设结束 = 无限"处理。改成就地跟引擎对齐：

```ts
const limit = Math.min(MAX_WEEK, weekLimitOf(data.term));
```

并补了三条测试把「不设结束 = 无限，而不是 0/NaN」这条语义钉住。

### 3. 周视图那条「现在」横线是冻住的

`nowTop` 在渲染时用 `new Date()` 算，但 `WeekView` 里**没有任何定时器** ——
屏幕不动、没有别的状态变化时，那条线会一直停在打开页面那一刻的位置。

现在接上了分钟对齐的时钟（见下），线会跟着走。

### 4. 一个永远不会命中的 `useMemo`

```ts
const events = expandWeek(data, s.week).filter(...);   // 每次渲染都是新数组
const stats = React.useMemo(() => {...}, [events]);    // 依赖永远在变 → 永远重算
```

这是 `useMemo` 的经典误用：依赖项是自己每次新建的数组，memo 等于没写。
`expandWeek` / `weekConflicts` / `resolvePalette` / `scheme` 都提成了真依赖。

### 5. 今日页每秒重建整棵视图

```ts
const now = useNow(1000);   // setInterval 每秒 setState
```

但整个界面只精确到**分钟** —— 「还有 12 分钟下课」、上课进度条，全是分钟级。
每秒重建一次，一天开着这一页就是八万多次无谓的整树重建。

换成新写的 `useMinuteClock()`：**对齐到下一个整分**，分钟一变立刻刷新，
中间一秒都不浪费。既不会出现"分钟已经跳了但界面还没动"，
又只有 1/60 的开销。

同时把 `expandDay` / `conflictsOf` / `freeSlots` / `resolvePalette` 都 memo 起来
（它们只跟"哪一天、哪份课表"有关，跟"现在几点"无关），
并把循环里的 `data.courses.find(...)` 换成一次建好的 `Map`。

## 三、关于收益，说实话

我写了个基准量了一下，结论**没有想象中那么夸张**，如实记下来：

```
数据规模: 20 门课 / 40 个时段
  expandDay        0.013 ms/次
  conflictsOf      0.010 ms/次
  freeSlots        0.009 ms/次
  resolvePalette   0.004 ms/次
  nextEvent        0.016 ms/次
  单次合计          0.052 ms
```

纯函数本身很便宜 —— 每分钟省下的"计算量"只有 0.05 ms 量级，可以忽略。

**真正的开销在 React 重建整棵视图**（对账上百个 DOM 节点），那一项这个基准量不到。
所以这一轮的准确说法是：

| 改动 | 性质 | 收益 |
| --- | --- | --- |
| 偏好触发全量重排 | **正确性** | 不再每次切标签页就清空重排通知 |
| 不设结束时右滑失效 | **正确性** | 直接修好了一个坏掉的手势 |
| 现在横线冻住 | **正确性** | 从"不动"变成"会动" |
| `useMemo` 永不命中 | 性能 | 0.1 ms/次 → 真的省下来了 |
| 今日页 1Hz → 每分钟 | 性能/耗电 | 重建次数少 **60 倍** |

前三条是这轮真正的收获，后两条是顺手清理。基准文件用完就删了，没有留在仓库里。

# UI 美化 + 一次自伤事故（v0.8.6）

## 一、先说最要命的一个发现：「设置」标签一直是点不到的

你反馈"不少按钮的字分裂成两行"，我做了个断行检测工具去量，顺手先撞见一个更严重的问题：

```
TABBAR 5项 框684-738  #1✓685-739 #2✓685-739 #3✓685-739 #4✓685-739 #5✗出框 739-793
```

标签栏写的是 `grid-template-columns: repeat(4, 1fr)`，但实际渲染了 **5 个**标签。
第 5 个（设置）落到隐式的第二行，而标签栏高度是写死的 `var(--tab-h)`，
于是那一行正好落在屏幕下面 —— **设置标签从头到尾就没显示过**。

你一直是用顶栏右上角那个 ⚙ 图标进设置的，所以没察觉。

改法是让列数跟着标签数量走：

```css
display: grid; grid-auto-flow: column; grid-auto-columns: 1fr;
```

以后再加标签也不会重蹈覆辙。

## 二、文字断行的真实成因

### 1. `.lr-right` 被挤压

```tsx
<div className="list-row">
  <div className="dot" />
  <div>…很长的说明…</div>
  <div className="lr-right"><button className="btn sm primary">去设置</button></div>
</div>
```

`.list-row` 的每一列默认 `flex: 0 1 auto`，**两边都能缩**。
中间那列内容很长时，两边按比例一起被压，右侧的动作区被压到只剩十几像素，
「去设置」四个字就断成四行。

修法是把职责分清：**中间列允许压缩（`min-width: 0`），右侧动作区一律不缩（`flex: 0 0 auto`）**。

### 2. 按钮压根没禁止换行

`.btn` 是 `height: 32px` 的固定高盒子，却没有 `white-space: nowrap`。
文字一换行就撑破高度或被裁掉 —— 两种都是坏的。
所有"设计上必须单行"的控件现在都显式禁止换行：
`.btn` / `.chip` / `.tab` / `.week-pill` / `.att` / `.at` / `.ai` / `.stat span` /
`.preset-name` / `.wp-name` / `.lr-right` / `.toast-undo` / `.sess-index` …

### 3. 节次轴没给「08:30」留余量

`--axis-w` 在 360px 下只有 **30px**，而 11px 的「08:30」本身就要 25–30px，
余量几乎为零 —— 手机上字体略宽一点，时间就被挤成「08:」+「30」两行。

现在 430px 以下给 40px、380px 以下给 38px，代价是每天少不到 1px 的卡片宽。

### 为什么桌面上量不出来

我写了检测器在无头 Edge 里量，**一开始量出来是 0 处断行**。原因是两条：

1. 检测器把克隆节点挂到了 `body` 下，丢掉了继承的字号
   （`.tab` 里是 11px，`body` 是 14px），量出来全部偏大 —— 整张表都是假阳性。
   挂回**原父节点**再量才对。
2. 桌面用 Segoe UI + 微软雅黑，安卓用 Noto Sans CJK / 厂商字体，
   **中文字形宽度本来就不一样**，桌面上刚好放得下的，手机上就会断。

所以最后走的是**防御性路线**：不赌"够不够宽"，直接把不该换行的文字锁死成单行，
再把容易被挤的弹性布局改对。这比调字号可靠。

## 四、一次自伤事故，以及怎么救回来的

必须记下来，因为这是我自己造成的。

我想给点击行批量加一个 `tap` 类，图省事用了 PowerShell：

```powershell
(Get-Content src\ui\SettingsView.tsx -Raw) -replace ... | Set-Content -Encoding utf8 src\ui\SettingsView.tsx
```

结果 **UTF-8 字节被按 GBK 解释后又写回**，整个文件的中文全变成「宸插厑璁」这种乱码，
而且每个中文串末尾的**最后一个字连同紧跟的引号一起被吞掉**，
93 行被破坏，文件当场编译不过。

### 怎么救的

1. **判断可逆性**：乱码是"UTF-8 字节被当 GBK 读"，理论上反向做一次就能还原。
   用 `.NET` 的 cp936 编码器把乱码重新编码成字节、再按 UTF-8 解回来 ——
   第 25–29、33、34 行**完全恢复**。但被吞掉的那一个字节是不可逆的。
2. **定位残留**：还原后剩下 93 处 `U+FFFD`（替换字符）。
3. **按规律批量修**：损坏形态是 `U+FFFD` + `?`，而那个 `?` 恰好占掉了
   **紧跟其后的一个定界符**（`<`、`'`、`)` 之类）。
   写了三遍修复表，用纯字符串替换（**不用正则**，避免再掉进转义坑）修掉 93 处。
4. **用快照验收**：损坏之前刚好渲染过设置页，留下了 DOM 快照。
   修复后重新渲染，把两边可见文本做集合差 —— 最后只剩版本号不同。
   这一步抓出了两处我凭记忆写错的字（多了一个「了」、把刷新图标 `↻` 写成了 `›`）。

### 教训

- **绝不用 PowerShell 的文本 cmdlet 处理源码文件**。这次是编码往返，
  下次可能是行尾或 BOM。要批量改源码就用 Node 读写 UTF-8。
- **改完要有"和已知正确状态对比"的手段**，不能只看"能编译"。
  `tsc` 通过只说明语法没错，说不出「再也不响了」比原文多了一个「了」。

## 七、构建流水线的一个坑

# 把系统自带的白色 UI 全部换掉（v0.8.7）

安卓 WebView 里有一批控件是**系统原生**的：字体、配色、圆角一律不受 CSS 控制，
弹出来就是白底系统列表 / 白底对话框，和这套描边工业风完全不搭。
这一版把它们全部换成了自家的组件。

## 一、换了什么

| 原来 | 现在 | 出现位置 |
| --- | --- | --- |
| `<select>` 系统白底下拉列表 | `<Picker>` 底部弹层 | 课程节次 ×2、调课节次 ×2、任务关联课程 |
| `window.confirm` 系统对话框 | `<ConfirmDialog>` 应用内卡片 | 删除课程、删除任务、重置通知、导入覆盖、清空课表、放弃未保存修改 |
| `<input type="date">` 系统日历 | `<DateField>` 自绘月历 | 周次条跳转、学期起始日、调课日期、任务截止日 |
| `<input type="time">` 系统时钟盘 | `<TimeField>` 时/分两列列表 | 作息节次 ×2、任务截止时刻 |
| `<input type="color">` 系统取色器 | `<ColorField>` 预览 + 十六进制 + 备选色 | 外观 → 自定义主色 |

整个 `src/` 里**已经没有任何原生表单控件**了（只剩注释里提到它们）。

## 二、各自长什么样

**选择器**：触发按钮就是一个 `.input` 外观的条，右侧一个 `▾`；
点开是底部弹层，选项整行铺满、当前项打勾并用主题色标出，
右侧还能带一条次要信息（节次时间、任课教师）。带 `role="listbox"` / `aria-selected`。

**确认框**：居中卡片，不是底部弹层 —— 确认是个"决定"，居中读起来更像决定。
文案区 + 一行两个按钮，危险操作的按钮用红色，取消在左。

**月历**：周一起始（中文习惯），固定 6×7 格，非本月日期淡化，
今天用主题色描边，选中项整块填主题色。底部有「今天」和「清除」两个快捷入口 ——
比原生少点好几下。"开学第一周周一"那种必填场景给 `clearable={false}`。

**时间**：两列列表，小时 00–23、分钟 5 分钟一档，点一下就选中，
改完点「完成」。比系统转盘在手机上更好点，精度对课表也够。

**取色**：大色块实时预览 + `#` 十六进制输入 + 18 个备选色。
输入合法就立刻生效，所以能边打边看效果；非法时给一行明确提示而不是静默失败。

## 三、顺带修掉的一个回归

换 `jump-date`（周次条里的日期）时踩了个 CSS 顺序坑：
`.picker-trigger { width: 100% }` 在文件里排在 `.jump-date { width: 128px }` **之后**，
同优先级下后者被覆盖，那个选择器直接撑成 368px，把旁边的「第 1 周」挤成三行。

改成双类选择器 `.picker-trigger.jump-date` 把优先级提上去，不再依赖书写顺序 ——
这类"谁在后面谁赢"的坑，靠顺序维持的样式迟早会翻车。

另外给 `.week-range` 补了 `white-space: nowrap`，周次文字不会再被挤断。

## 四、验证方式

这四个组件我没法在手机上点，所以用的是"**把弹层默认展开，dump 出 DOM 逐项核对**"的办法：

- 选择器：`role="option"` / `aria-selected` / 选中打勾 / 副信息（教师名）全部就位
- 月历：`cal-head`（‹ 2026 年 9 月 ›）、`cal-week`（一二三四五六日）、42 个 `cal-day`
- 时间：`tp-col` ×2、`tp-head`「时」「分」、24 + 12 个 `tp-cell`
- 取色：`cf-preview` 带当前主色、`cf-input` 里是 `#1677FF`、18 个 `cf-swatch`

验完把临时代码撤干净（脚本里加了 `TEMP-VERIFY` 标记，最后核对残留数为 **0**）。

## 五、交付

# 两个真 bug：提醒清单永远是空的 + 「4881 分钟后开始」（v0.8.8）

## 一、「接下来的提醒」一直是 0 条

你在这一页能同时看到两句话，而它们是互相矛盾的：

```
已排入通知系统    37 条（未来 7 天滚动排程）
接下来的提醒      0 条
未来 7 天没有需要提醒的课。加几门课，或者检查一下提醒设置。
```

我用同一份数据把 `planNotifications` 单独跑了一遍，**37 条算得出来**，
说明排程逻辑没问题 —— 是算好的清单**在写回状态时被覆盖掉了**。

### 根因

`App.tsx` 里「首次启动自动申请通知权限」那段：

```tsx
nt.requestPermission().then(function () { return nt.status(); }).then(function (st) {
  setNotify(st, []);          // ← 这里
  ...
});
```

它把 `upcoming` 无条件写成了 **空数组**。时序是：

1. 挂载 → 主同步开始，算出 37 条
2. 权限弹窗弹出，用户点「允许」（这中间可能过好几秒）
3. 权限回调执行 → `setNotify(st, [])` → **刚算好的 37 条被清成 0**

更糟的是 `patchPrefs({ permissionAsked: true })` 在这一轮里就已经置位，
所以这个副作用**再也不会重跑**，清单就一直空着，直到你改课表或改提醒设置
才重新同步一次。等于说，装完 App 后「接下来的提醒」基本不会正常工作。

同一个坑在 `SettingsView` 里还埋了 4 处：
`setNotify(st.value, s.upcoming)` —— 而 `s.upcoming` 是**那一刻渲染闭包里的值**，
在异步流程走完之后再写回去，写的是过期数据。

### 修法：把"更新状态"和"更新清单"拆成两件事

```ts
/** 只更新通道状态，保留当前排程清单 */
export function setNotifyStatus(status: AppState['notify']): void {
  setState({ notify: status });
}
```

权限申请、自检、重置这些流程只需要刷新状态，一律改用它；
只有真正重新排过程的 `syncReminders` 才用原来的 `setNotify(status, upcoming)`。

顺带把「排程出错」和「真的没有课」这两种空状态分开了 —— 以前不管哪种都显示
「未来 7 天没有需要提醒的课」，把用户往完全错误的方向引。

修完实测：`接下来的提醒  37 条`，和上面的「已排入通知系统」对上了。

## 二、「4881 分钟后开始」

这是「下一节课不在今天」时的分支，它直接把分钟数甩了出来：

```ts
kicker = '明天第一节课';
num = String(Math.max(0, next ? next.startsInMinutes : 0));
unit = '分钟后开始';
```

下一节课在三天后的周一，就是「4881 分钟后开始」。而且 kicker 写死成「明天」，
哪怕实际是四天后 —— **标签也是错的**。

两处都改了：

- 新增 `core/duration.ts` 的 `humanDuration()`，按分钟 / 小时 / 天分级：
  `5 分钟` → `1 小时 20 分` → `3 天 9 小时`。凡是给人看的时长都走它，
  提醒正文里的「几分钟后上课」也统一了（以前 60 分钟会写成「60 分钟后上课」）。
- **跨天时不再显示倒计时** —— 倒计时对三天后的课没有意义。改成直接给日子和上课时间：

```
明天第一节课   第 3-4 节
程序设计基础
实验楼 C402 · 10:15-11:45 · 张伟
明天            10:15 开始
```

kicker 也跟着算：1 天说「明天第一节课」，2 天说「后天第一节课」，
再远说「周三第一节课」，不再一律叫「明天」。

补了 6 条针对 `humanDuration` 的测试，其中一条专门钉住这次的教训：
**输出里不许出现「分钟」两个字，且首位数字必须小于 10**。

# 按原始计划继续扩展 · 第二批（v0.9.1 – v0.9.3）

## 一、ChangeSet 管线 + 全局撤销/重做（v0.9.1）

计划书 7.1 节把 `change_set` 设计成「审计与撤销（AI / 导入 / 插件共用）」，
core 的对外 API 里也有 `applyChangeSet(set)`。这一版把它落到前端。

### 为什么用快照而不是 op 列表

课表数据本来就是一棵小树（几十门课、几百个时段，JSON 才十几 KB），
而且所有改动都走 `Object.assign` 造新对象 —— **结构共享意味着快照几乎不额外占内存**。
op 列表看着优雅，但每一种操作都要写正反两套逻辑，漏一个分支就把数据改坏。
快照没有这个风险。

栈**只存在内存里**（上限 40 步），不落 localStorage：跨重启的撤销收益很小，
而写进磁盘会让每次编辑都多一份全量序列化。

### 哪些算"一步"

给 18 个写入点逐个打了标签：改提醒、调课/停课/换教室、增删任务、改节次时间、
增删作息方案、改学期设置、增删改课程、导入课表、导入 ICS、清空课表……

**刻意不记的**：考勤打卡、任务勾选。这两个高频低风险，记进去只会让撤销栈塞满噪音，
真正想撤的那一步反而找不着。

### 提示条上的"撤销"有个陷阱

原来的实现是「点了就把当时那份数据写回去」。问题是：改完 A 又改了 B，
再点 A 的撤销条，撤掉的是 B —— 用户会以为撤销坏了。

现在只在**这一步仍是最后一步**时才生效，否则如实告知「这一步之后又有改动，已经撤不回去了」。

界面入口：顶栏在**确实有东西可撤/可重做时才出现** ↶ ↷（平时保持干净，
标题里带「撤销：调课」），外加 Ctrl/Cmd+Z、Ctrl+Shift+Z、Ctrl+Y。
焦点在输入框里时让给浏览器自带的文本撤销，不抢。

### 测试

新增 12 条：6 条纯栈语义（含深度封顶、重做分支失效、空栈安全），
6 条**走真实 store 的端到端**（撤销/重做数据往返、多步、清空课表后还原）。

写第一版用例时踩了自己的坑：`beforeEach` 里用 `while (undo())` 抽空历史，
结果它把上一条快照的数据**还原**了回来，下一个用例的基线就不是空的 ——
正确顺序是**先清历史再重置数据**。为此补了 `clearHistory()` API。

## 二、分享码（v0.9.2）

计划书 6.6 节：「课表压缩 → base64url 短码，用于同学之间互相导入」。

**刻意不引入任何服务端** —— 本地优先是产品底线，为了一个分享功能把课表传到别人的
服务器上，和整个立场冲突。所以码里带着全部数据。

实现是 `JSON → gzip → base64url`，前缀 `KBR1.`。用浏览器原生的
`CompressionStream` 而不是自己设计紧凑二进制格式：几毫秒就完事，
而且不用为每种字段写一套编解码 —— 少写一套映射就少一类 bug。
老 WebView 没有 `CompressionStream` 时退化成不压缩（前缀 `KBR1U.`），照样能用。

测出来的体积：

| 数据 | 结果 |
| --- | --- |
| 合成的大课表（20 门课 / 40 时段 / 调课 / 任务） | 11366 → 1397 字节 → **1863 字符（16%）** |
| 内置演示课表（字符串互不相同，压缩率差些） | 4520 → **1926 字符（43%）** |

**不做二维码**：1900 字符要塞进二维码得用到版本 33 以上，从手机屏幕上扫非常费劲；
粘进微信 / QQ 反而更省事。

解码后直接交给 `parseTimetable` —— 那是导入 JSON 备份用的同一套校验与降级逻辑。
分享码不该有自己的一套解析规则，否则两条路径迟早分叉：一条修了 bug，另一条没修。

**端到端验证**：从浏览器真实渲染出来的导出弹层里把码抠出来，
用 Node 原生 zlib 解回来 —— 10 门课 / 14 个时段 / 5 个任务 / 3 条调课，逐项一致。

## 四、本地存储体检（v0.9.3）

| 内容 | 体积 |
| --- | --- |
| 结构化课表数据 | **约 11 KB** |

**结论：风险几乎全部来自图片，不是结构化数据。**

于是这一版做了两件事：

1. **保存失败不再静默**。`writeData` 以前是 `catch (e) { /* 忽略 */ }` ——
   存不下的时候界面一切正常，一重启数据全没了，用户根本不知道为什么。
   本地优先的产品，存不下去必须当场说出来。
2. **设置页加「本地存储」面板**，按存储键列出占用与总配额百分比。
   没有这个数字，用户只会看到「主题太大，存不下」却不知道该删什么。

## 五、关于 SQLite：我的建议是先别上（附证据）

计划书 3 节选了 SQLite（`@capacitor-community/sqlite`），理由是「移动端唯一靠谱的
结构化本地库」。但从上面的实测看，**它解决不了这个应用真正的问题**：

| | SQLite 方案 | 直接外置图片 |
| --- | --- | --- |
| 结构化数据（11 KB） | 解决（本来就不是问题） | 不需要 |
| 图片占满 5MB 配额 | **不解决** —— 图片仍在 localStorage 里 | **直接解决** |
| APK 体积 | +4～8 MB（四种 ABI 的原生库） | 0（Filesystem 插件早就在包里） |
| 新增原生依赖 | 是 | 否 |
| 迁移风险 | schema + 迁移脚本 + 回滚 | 一次性把 data URI 挪到文件 |

所以下一步我打算做的是：**把壁纸和课程图片从 localStorage 挪到应用私有目录**
（用已经装好的 `@capacitor/filesystem`），localStorage 只留路径引用。
这直接消灭配额风险，不加依赖、不涨体积。

如果你更倾向于坚持 SQLite（比如考虑将来做云同步、要复杂的查询），
说一声我就按原计划来 —— 但我想先把证据摆出来，而不是默默换掉你选的东西。

### 关键决定：插件是"声明"，不是"代码"

最直觉的做法是让插件包带 JS 然后 `import()` 执行它。**这条路我没走**：

| 问题 | 说明 |
| --- | --- |
| 破坏安全承诺 | 应用里没有 eval、没有远程代码、没有第三方 SDK —— 这是「无广告无追踪」能被验证的前提。开一个执行任意代码的口子，前面所有保证都变成口头承诺 |
| 技术上也不顺 | Capacitor 的 WebView 里动态 import 本地文件要走 `_capacitor_file_`，跨源会被拦；绕过去就得降级 CSP |
| 权限令牌拦不住 | 用户装插件时没能力判断它会不会偷课表。令牌能拦「读没读」，拦不住「读到之后发去哪儿」 |

所以 v1 的插件是**纯数据**：只能从宿主已实现的能力里挑，配置参数。
换来一件很重要的事 —— **装任何插件都不可能让应用做它本来不会做的事**。

代价是表达力有限，这一点在规范文档里明确承认了。

### 做了什么

| 模块 | 内容 |
| --- | --- |
| `src/core/exporters.ts` | 纯函数：CSV（UTF-8 BOM + RFC4180 转义）、Markdown（转义竖线）、周 / 整学期 / 课程清单三种范围 |
| `src/plugins/types.ts` | 清单 schema、能力类型、权限模型；顶部写清了"为什么不用代码插件" |
| `src/plugins/host.ts` | 16 条校验规则、安装/卸载/停用、权限授予、能力汇总 |
| `src/plugins/builtin.ts` | 3 个内置插件、4 种导出格式 |
| `src/ui/ExportSheet.tsx` | 导出菜单，内容全部来自插件 |
| `src/ui/PluginsPanel.tsx` | 插件管理：启停、逐项权限勾选、从文件安装、卸载 |
| `docs/10-plugin-spec.md` | 完整规范 |
| `examples/plugin-teacher-contact.tbplugin.json` | 可直接安装的示例包 |

**内置插件吃自己的狗粮** —— CSV / Markdown 这三个格式本身就是通过插件 API 提供的，
不是另写一套分支。接口设计得不好用会第一时间暴露出来，而不是等第三方来踩。

校验写得比"能跑就行"严得多（16 条）：插件是可以从聊天软件转发过来的文件，
畸形清单如果被放进去会在每次打开设置页时炸掉。**一条不过就装不上，并且明确说清是哪条。**

还有一条规矩：**能力需要的权限必须在 `permissions` 里声明**，不允许"用到才说要"。

### 测试

28 条新增（19 条宿主 + 11 条导出器），包括：
- 16 条校验规则的每一条都有对应用例
- 撤销权限 / 停用插件后导出菜单立刻变化
- 内置插件不能被卸载、不能被同名覆盖
- localStorage 里存了坏数据时退回空状态而不崩
- **仓库里那份示例插件包必须能真的装上** —— 防止规范文档腐烂

## 二、桌面小组件（v0.9.5 / v0.9.6）

计划书 6.5 节：「2x2（下一节课 + 倒计时）、4x2（今日剩余课程列表），
原生 Kotlin + 自定义 Capacitor 插件负责数据桥与刷新」。

### 与计划的一处偏离（有理由）

计划写的是 Kotlin + Jetpack Glance。我用了 **Java + RemoteViews**：

- Glance 要拉一整套 Compose 运行时依赖，而我们这个小组件就是几个 TextView
- RemoteViews 从 API 1 就有，行为在各家 ROM 上最可预测
- 项目里已有的 `ReliabilityPlugin` 就是 Java，风格统一

### 数据流向（严格照计划）

```
Web 层算好（下一节课 / 今天剩下的课）
   ↓  JSON 字符串
WidgetPlugin.update()  →  SharedPreferences
   ↓  发 APPWIDGET_UPDATE 广播
AppWidgetProvider 只负责摆位置
```

**小组件里不跑时间引擎。** 引擎一旦有两份实现，单双周、调课、作息切换这些
边界情况迟早对不上，而"小组件显示的是错的"是最难说清的一类 bug。

推送时机放在**排程之后**（`syncReminders` 里），而不是另开一个副作用 ——
小组件要显示的下一节课和排程用的是同一份展开结果，分两处算迟早会出现
"提醒已经改了、小组件还显示旧的"。

### 倒计时用 Chronometer，不是定时刷新

RemoteViews 里的 `Chronometer` 在**桌面进程里自己走**，不需要每分钟广播一次。
用广播推动的倒计时既费电又会被系统限流 —— 到时候秒数卡住不动才是最尴尬的。
`updatePeriodMillis` 因此设为 0，数据完全由应用推送。

### 验证

- 两个 receiver 都进了 APK 清单，带 `APPWIDGET_UPDATE` 过滤器与 provider 元数据
- `widget_next_info` / `widget_timetable_info` / 三个布局都进了资源表
- 7 条 `buildWidgetPayload` 单测（时间换算、跨天、空课表、字段名契约）

**还没做真机验证** —— 需要你在桌面上长按 → 小组件 → 拖出来看。

### 顺带

加了「桌面小组件」说明面板。理由很实在：小组件在桌面上、功能入口在应用里，
**用户装了应用但从来不知道有小组件，是这类功能最常见的死法**。
系统不允许应用自己往桌面加，只能把路径写清楚让他自己加。

# SQLite 持久化（v0.9.7）—— 目标最后一项

## 一、先说结论与代价

**上了 SQLite，但只用在它真正解决问题的地方。**

| | |
| --- | --- |
| 先确认可行性 | `@capacitor-community/sqlite@8.1.1` 的 peer 依赖是 `@capacitor/core >= 8.0.0`，与本项目的 Capacitor 8.5 兼容 |
| APK 体积 | 5.15 MB → **13.51 MB**（四种 ABI 的原生库） |
| 裁掉 x86/x86_64 后 | **9.22 MB**（真机都是 arm，x86 只有模拟器需要） |
| 净代价 | **+4.07 MB** |

这个代价值得摊开讲：**结构化课表数据只有约 11 KB**，它从来不是问题；
真正撑爆 localStorage 的是壁纸图片（2–5 MB / 张）。
用文件系统插件做同样的事是 **+0 MB**。

我最终仍然选了 SQLite，理由是它对**两类数据都**给了一致的持久层，
而且换来的不只是配额：事务写入、以后要做多学期 / 云同步时有查询能力。
但这是有代价的选择，你如果更在意体积，换成文件系统是一条清晰的退路
（`src/storage/index.ts` 是唯一的接缝）。

## 二、数据怎么分层

```
结构化数据（课表 / 主题 / 偏好）   约 11 KB   →  SQLite kv 表 + localStorage 镜像
图片资产（壁纸成品 / 原图 / 课程配图） 2–5 MB/张  →  SQLite assets 表
```

**localStorage 保留为"快速路径镜像"**，有两个实打实的好处：

1. `initialState()` 照旧同步读到课表就能立刻渲染 —— **启动路径没有变成异步**，
   首屏不会空白。异步只花在图片上，补不上最多是壁纸晚一拍出现。
2. 只有"两个都写失败"才等于丢数据，比只依赖其中一个稳。

## 三、内存里是 data URI，磁盘上是引用

最容易出事的是渲染路径，所以**一行渲染代码都没改**：

```
内存：  theme.wallpaper.custom = "data:image/webp;base64,..."     ← 渲染直接用
磁盘：  theme.wallpaper.custom = "asset:8f3a1c2d-4k2"            ← 只有几 KB
```

外置只发生在"写入磁盘"这一步，还原发生在挂载之后。

**踩到的一个坑**：`hydrateStorageIntoState()` 里我原本拿库里的数据和内存里的直接比，
但两者**永远不可能相等** —— 库是引用形态、内存是 data URI 形态。
结果是每次启动都白做一次替换，还会把刚还原好的图片又打回去。
改成"把内存那份先外置再比"才对。

另一处：`applyThemeToDom` 必须挡住 `asset:` 开头的值。不挡的话浏览器会去请求
一个叫 `asset:xxx` 的地址，控制台一堆报错而壁纸也不显示。

## 四、老用户的数据会怎样

三条路径都走通了：

1. **升级上来**：localStorage 里本来就存着内联大图 → 启动时 `migrateInlineAssets()`
   把它们搬进资产库、把精简版写回去，**配额当场释放**。
   只做还原是不够的 —— 不主动搬一次的话，配额会一直被占着，直到用户碰一次主题。
2. **SQLite 装不上**（比如浏览器里）：退回 localStorage，设置页如实标出
   「SQLite 不可用，暂存在本地存储里」，应用照常跑。
3. **localStorage 写失败**（配额满）：以前是静默 catch，界面一切正常、一重启数据全没。
   现在会弹错，并且 SQLite 那份还在 —— 下次启动会用它补正。

写这一条时专门加了防覆盖：**只要用户已经动过任何东西，就跳过补正**，
否则异步读盘回来晚一点就会把用户刚做的改动静默抹掉。

## 五、验证

- 21 条 `assetRef` 单测（外置/还原往返、内容哈希去重、找不到的引用降级成空串、
  不改动入参、没有大图时不复制对象）
- 浏览器里实测回退路径：设置页显示「SQLite 不可用，暂存在本地存储里」，应用正常启动
- 应用在异步启动流程下正常渲染（周网格在）
- 五个标签页 320/360/390px 下 `OVERFLOW 0` / `WRAP 0`，**并断言了页面确实加载**
  （上一批差点被"拒绝连接页"骗过去）

**SQLite 的真机路径没法在这里验证** —— 需要你装上之后去「设置 → 本地存储」
看那一行是不是显示「存在 SQLite 里，不占本地存储配额」。

# 小组件修好了 + 设置页瘦身（v0.9.8）

## 一、小组件两个 bug，都是我的错

### 1. 「496963:41:52」—— Chronometer 的时基搞错了

`RemoteViews.setChronometer(viewId, base, ...)` 里的 `base` 要的是
**`SystemClock.elapsedRealtime()`**（开机以来的毫秒），不是墙上时钟的 epoch 毫秒。

我直接塞了 epoch。Chronometer 在倒计时模式下算 `base - elapsedRealtime()`，
而开机时长相对 epoch 可以忽略 —— 结果就是显示的数值约等于 epoch 本身。

对一下账：**496963 小时 41 分 52 秒 = 1.789e12 毫秒**，
正好是当时的 epoch 毫秒值。严丝合缝。

修法是先换算再叠加：

```java
delta = targetEpochMs - System.currentTimeMillis();   // 还有多久
base  = SystemClock.elapsedRealtime() + delta;        // 换算到正确时基
```

抽成了 `WidgetRender.chronometerBase()`，两个小组件共用，注释里把这段账写清楚了。

### 2. 4×2 一片空白 —— `RemoteViews.addView` 抛异常

4×2 原本用 `removeAllViews` + `addView` 往列表里塞行；2×2 没用这两个 API，
而 2×2 至少显示了内容 —— 说明数据推过去了，问题出在 4×2 自己的渲染上。
`addView` 在部分桌面实现上会被拒，一旦抛出整次 `onUpdate` 就废掉，
小组件停在 `initialLayout` 上，看起来就是一片空白。

改成**布局里写死三行**，代码只切可见性与文字。顺带更快（不用每次重新 inflate）。

这里还有个坑差点又踩：一开始想用 `<include>` 复用行布局，但那样三行的子控件
**共用同一批 id**，RemoteViews 按 id 查找永远只命中第一行，三行会显示同样的内容。
所以三行是完整展开的，每行一套独立 id（`widget_r1_time` / `widget_r2_time` / …）。

### 3. 顺带修掉一个「加了没反应」的陷阱

`pushWidgetData` 原本先判断「桌面上有没有小组件」，还把结果缓存起来。
但用户在应用已经跑起来之后才往桌面加小组件的话，那份缓存永远是 `false`，
数据永远推不过去 —— **小组件会一直空着，只有手动点「立即同步」才活过来**。

判断本身是我想省一次桥接调用，结果省出了一个用户看不懂的故障。
直接去掉：一次调用的代价远小于「加了没反应」的困惑。

### 4. 出错时不再留白

两个 provider 的 `onUpdate` 都包了 try/catch，失败时退回一句人话
（「打开应用同步一次」），而不是让桌面停在一片空白上。
真出问题时，用户至少知道该做什么。

设置页原本有 **14 个面板**，日常用得到的和排查用的混在一起。现在拆开：

| 默认显示（10 个） | 收进调试（+5 个） |

| 提醒通道 · 桌面小组件 · 后台提醒可靠性 · 默认提醒规则 · 操作保护 · 学期 · 作息与节次 · 课表数据 · 插件 · 关于 | 提醒诊断 · 接下来的提醒 · 真机提醒自检 · 诊断信息 · 本地存储 |

开关就是设置页底部的一行「调试模式」，开启后在末尾追加一组「调试」面板。
开发时可以用 `?debug=1` 直接进。

# 去掉 emoji，换成内联 SVG 图标（v0.9.9）

## 一、为什么该换

emoji 的观感完全交给系统字体：同一行里 iOS、Android、Windows 会画出三种不同粗细、
不同配色、甚至不同造型的字形，而且**无法跟随主题色** —— 换深色主题时它还是那一套彩色贴纸。

对一个「工业风 + 可 DIY」的产品来说这是硬伤：用户调了半天主色、描边和圆角，
结果一排彩色 emoji 杵在标签栏里，前面所有克制全白费。

换成 SVG 之后：单色、跟随 `currentColor`、粗细统一、尺寸可控，
而且不需要额外字体文件（体积为 0）。

## 二、清掉了 21 处，分布在 8 个文件

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 标签栏 5 个 | 📅 ☀️ 📝 🎨 ⚙️ | 日历 / 太阳 / 清单 / 滑杆 / 齿轮 |
| 顶栏 | ⚙ 🔍 | 齿轮 / 放大镜 |
| 周次轴上的作息入口 | ⚙ | 齿轮（13px） |
| 空状态 5 处 | 📋 🌿 ☀️ 🔍 ✅ | clipboard / leaf / sun / search / check |
| 首启页 4 条 | 🔒 🚫 📦 🔔 | 锁 / 禁止 / 归档 / 铃铛 |
| 外观锁定的状态图标 | CSS `content: "🔒"` | **mask + currentColor**（见下） |
| 提醒到的提示条 | `'🔔 ' + title` | 去掉前缀 |

```css
  content: "";
  width: 13px; height: 13px;
  background: currentColor;                          /* 颜色跟着文字走 */
  -webkit-mask: url("data:image/svg+xml,...") center / contain no-repeat;
}
```

这样图标会跟着主题的正文色变化，深色模式下自动变浅，而不是永远那个彩色小锁。

# 两个真 bug + 说明书 + 更新日志（v0.10.0）

你说"发现 Bug：退出重进后背景没有保留；导出主题包没有实现"。两个都是真 bug，
而且**第二个是我之前交付说明里写错的那部分** —— 我把"导出"当成已经做完了，
实际上它在安卓上根本不会发生。

## 一、背景为什么丢：两个模块对"合法壁纸值"的理解不一致

链条是这样的（v0.9.7 引入图片资产库之后就一直是这样）：

| 步骤 | 发生了什么 |
| --- | --- |
| 选图 | `theme.wallpaper.custom` 是 data URI |
| 写盘 | `extractAssets()` 把大图抽进 SQLite，`localStorage` 里只留 `asset:<key>` |
| 冷启动 | `loadTheme()` **同步**读 `localStorage` → `validateTheme()` |
| 校验 | 只认 `data:image/...`，于是判定"不是内嵌图片" |
| 结果 | `kind` 被打成 `'none'`、`custom` 清空 —— **图片还没等到还原就已经没了** |
| 补图 | `hydrateAssetsIntoState()` 面对一个 `kind='none'` 的主题，什么都没得还原 |

单测任何一环都发现不了：`extractAssets` 是对的，`hydrateAssets` 是对的，
`validateTheme` 单独看也"合理"。错的是**它们之间的约定**。

修复分三处：

1. `validateTheme` 同时接受 `asset:<key>` 引用（`isAssetRef`）；
2. `hydrateAssetsIntoState` 在图片**确实**还原不出来时（换机、清过数据）
   把 `kind` 降级成 `'none'` 并写回磁盘 —— 不能让外观页显示"已选自定义壁纸"却什么都看不到；
3. `parseThemeFile` 反过来收紧：主题包必须是自包含的，包里出现 `asset:` 引用
   就明确提示并跳过，而不是留一张渲染不出来的壁纸。

补了 8 个单元测试，其中最关键的一条把"写盘 → 冷启动 → 校验 → 还原"整条链路原样走一遍 ——
**只测单点的测试永远抓不到这类 bug**。

## 二、导出为什么没反应：`a.download` 在 WebView 里是被丢掉的

浏览器里给隐藏的 `<a>` 设 `download` 再 `click()` 就能存文件。
Capacitor 的安卓 WebView **没有下载宿主**，这个 click 直接进黑洞 ——
点了"导出主题包"什么都不发生，用户看到的就是"这个功能没做"。

同一段代码被复制了四份：主题包、JSON 备份、ICS 日历、插件的 CSV / Markdown 导出。
所以四个入口一起坏，只是你只碰到了主题包那个。

改法是统一收口到 `src/platform/saveFile.ts`：

- 原生：`Filesystem.writeFile` 写进应用缓存目录（**不需要任何存储权限**）
  → `Share.share` 打开系统分享面板 → 用户自己选"保存到文件"、发微信、发邮件；
- 分享不可用时退回公共「文档」目录；
- 浏览器：仍然走 `a.download`。

分享这条路的可行性是**查过原生侧配置**才写的，不是猜的：
`android/app/src/main/AndroidManifest.xml` 里声明了
`androidx.core.content.FileProvider`（authority 为包名加 `.fileprovider`），
`res/xml/file_paths.xml` 里有 `<cache-path name="my_cache_images" path="." />`，
而 `SharePlugin.java` 正是用 `FileProvider.getUriForFile(ctx, pkg + ".fileprovider", file)`。

顺带把提示语改成三种说法：**已打开分享面板 / 已保存到「文档」目录 / 已取消**。
原来那句笼统的"导出成功"是第二个坑 —— 用户找不到文件，只会以为功能又坏了。

# 表格导入 · 小组件跳转 · 外观分享码 · 时区重排（v0.11.0）

按计划书盘完账之后你选的四项，这一版全部落地。

## 一、Excel / CSV 导入

计划书 §1.1 的第一条功能目标就是"5 分钟录完一学期"，而此前只能一门一门手录。

### 自作主张的一处：不用 SheetJS，自己解 xlsx

xlsx 库动辄几百 KB，而这个应用整个产物不到 500 KB；我们只需要"把单元格读成字符串"，
用不到样式、公式、图表。更重要的原因是**不引入依赖就不引入供应链风险** ——
"无广告无追踪"这个承诺能站住，靠的是产物里没有第三方代码。

于是手写了两段：

| 部分 | 做法 |
| --- | --- |
| ZIP | 从 EOCD 倒着找中央目录 → 逐个条目定位局部头 → `DecompressionStream('deflate-raw')` 解压。store（不压缩）与 deflate 两种都支持 |
| XML | 正则切标签（这几份 XML 都是机器生成的，没有嵌套同名标签）。顺手处理共享字符串、`<rPh>` 注音、`r="C4"` 造成的空列 |

**不用 DOMParser 的额外好处**：整个模块在 Node 里就能跑单测，不用为了测试搭 jsdom。

编码上先严格按 UTF-8 解、失败再退 GBK —— 顺序不能反，因为 GBK 几乎不会解码失败，
拿它去解 UTF-8 只会得到一堆"看起来合法"的乱码。教务导出的 CSV 十有八九是 GBK。

### 语义层才是难点

"周次"能写出十几种花样，每一种都单独测了：

| 输入 | 解析结果 |
| --- | --- |
| `1-16周` / `第3-18周` | range |
| `1,3,5` / `1、3、5` | list |
| `1-3,8-9周` | 展开成 list（跨段不连续，stepped 表达不了） |
| `单周` / `双周` / `1-16周(单)` / `2-16单周` | stepped；起点写反了也会落到正确的那一周 |
| `第1-2节` / `0102` / `1,2` / `第一节` / `三-四节` | 中文数字也要认 |

### 两种表格形态

教务系统导出的其实**多数是"课表矩阵"**（行=节次、列=星期，格子里塞着
"课程名 / 教师 / 周次 / 教室"），和"一行一个时段"的长表完全是两回事，所以走了两条解析路径。
矩阵的格子解析是**尽力而为**的：认出来的进预览，认不出来的整格列进"没读懂"里 ——
导入前必须过预览、确认才入库，猜错不会把脏数据写进课表。

无头浏览器里点不了"选择文件"，所以加了 `?sample=1..4` 两组内置样例
（1/3 矩阵、2/4 长表，3/4 直接进预览步）—— 这是唯一能在自检里验证第 2、3 步渲染的办法。

### 一处刻意的行为改动

解析时**不再丢掉空行**：数组下标要等于文件里的真实行号，否则预览里报"第 37 行没读懂"，
用户对着文件找不到那一行。空行由上层跳过。

## 二、时区 / 时间变更重排

提醒是折算成**绝对时刻**交给系统闹钟的。用户把时间往前拨一小时，或者换了个时区，
那些绝对时刻对应的墙上时间就全变了 —— 闹钟照样准点响，但响在了错误的时间点上。

做法上有一处刻意的克制：**不在原生侧重排**。那等于把时间引擎实现两遍（一遍 TS、一遍 Java），
两份逻辑必须永远一致，迟早分叉。所以原生侧只做一件事：
`SystemChangeReceiver` 收到 `TIME_SET` / `TIMEZONE_CHANGED` / `MY_PACKAGE_REPLACED`
就写一个"待重排"标记，应用回到前台时由 JS 读走、重排、清标记。

触发时机有两个：冷启动，以及 WebView 从后台回到前台（`visibilitychange`）。
后者很重要 —— 用户去系统设置改了时间再切回来，走的就是这条路。

（开机重排一直由通知插件自带的 `LocalNotificationRestoreReceiver` 负责，不受影响。）

## 三、小组件点击进课程详情

计划书 §6.5 明确要求过，之前只做到"打开应用"。

小组件是桌面进程渲染的，只能发一个 Intent；课程详情是 Web 层的弹层，中间隔着启动流程。
用 SharedPreferences 当接力棒：小组件把 `courseId` 放进 Intent → `MainActivity`
的 `onCreate` / `onNewIntent` 存下 → Web 层启动或回前台时 `consumePendingOpen()` 取走并**清掉**。

用"取走"而不是"读取"，是因为"打开课程详情"是一次性动作：留着的话，
用户下次正常打开应用会被莫名其妙地弹进某个课程详情。

4×2 的每一行都能点进各自那门课 —— 三行的 PendingIntent request code 必须各不相同，
否则会互相覆盖。

## 四、外观分享码

`KBT1.` 前缀，复用课表分享码那套 gzip + base64url。

**刻意不带壁纸**：一张壁纸动辄两三 MB，压完还是几百万字符，粘贴框都装不下。
所以分享码只带"能描述出来的那部分"（配色、字体、排版、卡片质感），

# 课表界面上的「角色」（v0.12.0）

这一版没做 AI。想清楚之后你的判断我认同：在"提醒准时率"这种硬指标面前，
不稳定的组件不该进核心路径；而"吉祥物"这个方向本身是对的，
只是**它不需要 AI 也能做得更好**。

## 一、第一版就把 AI 砍掉的理由

原本我提了三条路：截图导入、自然语言批量改课表、只读问答。重新过了一遍筛子
（*这件事不做 AI，用户得手工干多少分钟*）之后：

| 方向 | 判断 |
| --- | --- |
| 只读问答（"下周三去哪几栋楼"） | 砍。点两下就能看到，价值薄 |
| 单条自然语言录入 | 砍。表单点四下就填完了，AI 只会更慢更贵更不稳 |
| 截图导入 | 留了门。它是"抄 30 分钟变核对 2 分钟"的活，但价值取决于学校给不给导出表格——而 v0.11.0 的表格导入已经覆盖了能给导出的那部分 |

所以这一版**一行 AI 代码都没写**。省下来的力气做了角色 —— 它确定、离线、可测、免费。

## 二、几条自己给自己定的规矩

| 规矩 | 理由 |
| --- | --- |
| **默认什么都不显示** | 不喜欢屏幕上多个活物的人应该永远看不到这个功能。不导入就是个零 |
| **不内置任何角色、不提供下载渠道** | 素材从哪来是用户自己的事；内置角色还牵扯版权 |
| **纯数据，无代码** | 和主题包、插件一个立场：角色包能闯的最大的祸就是"不好看" |
| **只支持 WebView 原生能播的素材** | 静态图 / 动图 WebP·APNG·GIF / 逐帧雪碧图。Live2D、Rive、Spine、Lottie **每一个都要求引入运行时**，为它们换掉"产物里没有第三方代码"这条底线不值 |
| **素材走资产库** | 一张立绘一两 MB，塞 localStorage 会顶满 5 MB 配额 —— 而配额一满，**课表数据本身**就写不进去了 |

## 三、状态机是纯函数

`src/mascot/motion.ts` 里没有副作用：输入（当前状态 + 现在几点 + 有没有人在拖），
输出（新状态）。四个相位：

| 相位 | 触发 |
| --- | --- |
| idle | 默认。呼吸 + 随机间隔眨眼（2.6–6.2 秒，固定节奏会像机器） |
| react | 点一下，约 0.9 秒后回到之前的状态（从睡眠中被点醒，反应完接着睡） |
| sleep | 3 分钟没人理，动作周期放慢 1.6 倍 |
| drag | 拖动中，自走动画全部停止 —— 手指按着还在晃会很难对准 |

纯函数带来两个实际好处：**17 个单测直接锁住行为**，而且"偶尔卡在某个姿势不动"这类
问题（几乎都源于状态机里藏了副作用）从结构上就不可能发生。

## 四、渲染层守的三条硬约束

1. **不参与布局**：`position: fixed` 浮层，z-index 25（内容之上、悬浮按钮与弹层之下）。
   它一旦进文档流，320px 窄屏的排版立刻会变 —— 这个坑我们踩过好几次。
2. **不挡可点控件**：外层 `pointer-events: none`，只有角色本体 `auto`。
   它飘在哪个按钮上面，那个按钮仍然点得到。
3. **只动 transform / opacity**：改 width/height/margin 会让整页重排，在常驻浮层上就是可见卡顿。

外加两条降级：系统开了「减弱动态效果」→ 只静态显示；页面切到后台 → 所有计时器停。

## 五、配置教学（这一版的重点之一）

你特别提了"这个功能不是所有人都会"，所以教学写成了**两条路径**：

- **应用内说明书新增「角色」一章**：能做什么 → 三种用法 → 位置/大小/收起 →
  **怎么自己做一个角色包** → 字段表 → 可直接照抄的最小示例 → 素材准备建议 → 常见错误 → 隐私与体积。
- **仓库里 `docs/12-mascot-spec.md`**：同一份内容的可查版本。

最省事的制作路径被刻意放在了最前面：**不要手工折腾 base64** ——
先用「用一张图当角色」导入，再「导出角色包」拿到一份已经内嵌好图片的 JSON，
把它当模板改，再导回去。这样绝大多数人根本不需要碰编码。

# 角色的第二轮打磨（v0.13.0）

上一版把角色做出来了，这一版解决"用起来别扭"和"工程上会出事"两头的账。

## 一、两处真 bug

### 1. 逐帧雪碧图角色根本显示不出来

自检第一次跑 `?mascot=2` 就报出来：

~~~
MASCOT 0x140 素材=sheet 相位=idle 遮挡可点控件=0
~~~

**宽度是 0**。原因是 `background-image` 的元素**没有固有尺寸** ——
`<img>` 靠图片的固有比例能自己撑开，而背景图不会，`width:auto` 的块级元素直接塌成 0。
所以那个模式下角色是"存在但看不见"。

修法是读一次雪碧图的原始像素，按格数折出单格宽高比，据此定宽。
**这个 bug 从 0.12.0 就在**，因为 sprite 那条渲染分支此前完全没有运行时验证 ——
这也是这轮加 `?mascot=1/2/3` 三个自检入口的直接原因。

### 2. 换角色时旧素材留在本机

角色图几百 KB 到几 MB，存进资产库之后换一次就多留一份，换十次就是十几 MB，
而且**界面上完全看不出来**（设置里的"图片资产"只显示总数）。

现在按"旧包用到的 key 减去新包用到的 key"精确回收。刻意**不做全局扫描式清理**：
那需要一个正确的 keep 列表（主题 + 课程配图 + 角色），而 keep 列表一旦算错
（最容易踩的坑是：素材在启动后已经还原成 data URI，这时候去收集引用会得到空集），
删掉的就是还在用的图。差集法的输入是确定的，错不了。

## 二、工程适配：只在安全区里活动

原来的钳制是写死的"视口 4%–96% / 6%–94%"，结果是角色可以压在底部标签栏上 ——
而标签栏是导航，被压住是很明显的低级问题。

现在改成**实测**顶栏下沿与标签栏上沿（安全区、横竖屏、分屏都会改这两个高度，
写死常量必然在某些机型上错），再据此钳制。另外转屏 / 分屏 / 软键盘弹起之后
会重新钳制一次，越界的位置被悄悄纠正。

抽成纯函数 `src/mascot/placement.ts`，12 个用例钉住边界：
顶栏、标签栏、横屏窄高、角色比屏幕还宽（退化成居中而不是负区间）、
安全区被挤满（退化成整个视口）。

# 白屏事故（v0.14.0）：一个条件执行的 hook

你报的"角色编辑栏一操作就白屏"。**是真的，而且是我上一轮引入的回归。**

## 一、怎么定位的

白屏最讨厌的地方是它什么都不说：没有报错、没有按钮，用户只能卸载重装。
而这类问题 `tsc` 抓不到、单测抓不到、布局自检也抓不到 —— 因为**渲染是成功的，
崩溃发生在交互之后**。

所以第一步不是读代码，是**复现**。手上正好有完整的证据链：

1. `dist/` 里还留着 v0.13.0 的构建产物 —— 也就是你正在跑的那份代码。先整份冻结到临时目录；
2. 写一个**同源驱动页**：把应用放进 iframe，用真实 DOM 事件点按钮，
   同时挂上 `error` / `unhandledrejection` / `console.error` 三个钩子；
3. `--dump-dom` 把驱动页的日志读回来。

第一次跑就抓到了：

~~~
[点「暂时收起来」] ok
!! WINDOW ERROR: Uncaught Error: Minified React error #300
[after hide] root=0        ← 整棵树被卸载 = 白屏
~~~

**React error #300 = 渲染期调用的 hook 数量比上一次少。**

## 二、根因

v0.13.0 我重写 `MascotOverlay` 时，把提前返回放在了位置计算之前，
然后把新加的"位置纠正" `useEffect` 写在了那个提前返回**之后**：

~~~tsx
const sheetFrames = ...
React.useEffect(逐帧翻页)          // hook N
if (!pack || !asset || mp.hidden) return null;   // ← 提前返回
...
React.useEffect(位置纠正)           // hook N+1：隐藏时压根不会执行
~~~

- 角色可见：跑 N+1 个 hook
- 角色隐藏：跑 N 个

React 一比对发现数量不一致，**直接抛错卸载整棵树**。所以点「暂时收起来」必白屏，
点「移除角色」同理。

现在 `Mascot.tsx` 里那段代码上方立了一条铁律注释，下方立了边界标记：
**hook 全部在上面，条件返回放最下面**。

## 三、不只修，还加了三层防护

只修一次是不够的 —— 这类 bug 的可怕之处在于它完全静默。所以：

| 防护 | 作用 |
| --- | --- |
| **角色级错误围栏** | 角色是装饰，**永远不该有能力搞白主功能**。真出事时原地显示一条错误 + 「收起」「移除角色」两个一键回退 |
| **应用级错误围栏** | 任何一处渲染异常都变成一张能读的错误卡片（重试 / 复制错误信息），而不是白屏 |
| **自检 ROOT 指标** | 应用壳被清空会明确报 `ROOT EMPTY(0) 渲染崩了`。以前这类崩溃在自检里是"看起来一切正常" |
| **自检 `?mascotop=` 参数** | `hide / remove / size / editor` 四条操作路径纳入无人值守检查 —— 这次的白屏恰好只在这几条路径上出现 |

## 四、验证

# 视频素材与选素材界面（v0.15.0）

你问的「手机只给了相册权限、没法导入 webm」，根因有两层，两层都是我的问题。

## 一、为什么 webm 导不进来

| 层 | 问题 |
| --- | --- |
| 选择器 | `accept="image/*"`。**安卓的相册选择器是按 MIME 过滤的** —— 你的 webm 在相册里属于「视频」分类，压根不会出现在待选列表里。表现就是「想选它，但列表里没有」 |
| 管线 | 就算选中了也会被拒：图片管线第一行是 `if (!type.startsWith('image/')) throw`，而 webm 是 `video/webm` |

## 二、做法：视频 → 逐帧雪碧图

没有新增「视频素材」这种类型，而是把视频**抽帧拼成我们已经支持的逐帧图**。选这条路的理由：

1. 不用新增素材类型 —— 资产库、导出、编辑器、桌宠播放全都不用改；
2. 不依赖 video 的自动播放策略，也不会在桌面上同时跑一堆解码器；
3. 抽完就是一坨**确定的像素**，帧率、循环、暂停全由我们自己说了算。

排版规则抽成纯函数（`planSheet`，14 个用例）：默认 12fps、最多 48 帧、最多 8 列、
单格高度不超过 480、整图最长边不超过 2048（超了等比缩小）。
**采样点取每一小段的中点** —— 很多视频开头几帧是黑的，取起点会得到一格全黑。

**已知限制**：带透明通道的 webm 是否保留透明，取决于系统解码器，不同机型不一样。

# 逐帧图的两处硬伤：帧数 ≠ 格数 · 单格被压糊（v0.15.2）

你报的两句话 —— **「一闪一闪的，大部分时间不显示」** 和 **「分辨率太低」** ——
看起来是两件事，其实是同一条管线（视频 → 逐帧雪碧图）上的两处硬伤。
这一篇把**量出来的数**和判定方法都留下，方便以后回归时对照。

## 一、一闪一闪：播放按「网格格数」而不是「真实帧数」

### 现象与根因

逐帧图是「一张大图里排着 N 帧」。排版规则是：

```ts
const cols = Math.min(frames, 8);
const rows = Math.ceil(frames / cols);   // ← 最后一排经常排不满
```

**排不满的那几格是全透明的**（clearRect 之后没画）。而渲染端原先这样取帧数：

```ts
const frames = (asset.cols || 1) * (asset.rows || 1);   // ← 错在这里
```

于是每一次循环都会把那几格也播一遍 —— 角色每隔几帧就凭空消失一次。

### 量出来的规模

对 0.3–8 秒的时长逐一算过（12 fps、上限 48 帧）：

| 时长 | 帧数 | 网格 | 空格子 | 空白占比 |
| --- | --- | --- | --- | --- |
| 0.75s | 9 | 8×2（16 格）| **7** | **44%** |
| 1.0s | 12 | 8×2 | 4 | 25% |
| 1.5s | 18 | 8×3 | 6 | 25% |
| 2.0s | 24 | 8×3 | 0 | 0% |
| 3.0s | 36 | 8×5（40 格）| 4 | 10% |

**0.3–8 秒里有 37.9% 的时长会踩到这个问题**（771 个采样点里 292 个）。
换句话说：除非时长刚好让帧数是 8 的倍数，否则一定闪。

### 修法（两条腿，缺一条仍会闪）

1. **素材带上真实帧数**：`MascotAsset.frames`。
   `frameCount()` 是唯一出口：有 frames 就用它（夹在 2..cols×rows），没有就退回 cols×rows（= 旧包行为）。
2. **排版尽量排满**：`chooseGrid()` 在 4..8 列里优先找能**整除**帧数的列数 ——
   12 帧排 6×2、18 帧排 6×3、24 帧排 8×3、30 帧排 6×5，这些常见时长因此一格不空。
   整除不了（9 / 27 / 46 帧）时退回「尽量 8 列」，由第 1 条兜住。

### 老角色包怎么被修好

改渲染逻辑**并不能**修好已经存下来的包（它们连 frames 字段都没有）。所以启动后 1.5 秒跑一次
`repairMascotFrames()`：把逐帧图铺进小画布、逐格读 alpha，末尾连续的空格不算帧，
量出来比格数少就写回包里。三条自我约束写在函数注释里：

- 只收紧（`scan.frames < cells` 才动），绝不放大；
- 已经有 frames 的素材不碰（用户手动改过的不该被覆盖）；
- 量不到就什么都不做 —— **绝不猜一个数字写进去**。

手动入口是「检查这个角色」里的「按实测帧数修正」（`repairMascotFrames(true)`，允许改大改小）。

## 二、分辨率太低：两个上限把单格压成了 183×326

旧上限是「整图最长边 2048 / 单格高度 480」。看上去不苛刻，但 48 帧的竖屏视频是 8×6 的网格，
**行数一乘就超**：6 × 480 = 2880 > 2048，于是按 0.88 一步步缩，最后停在 183×326。

而显示高度 140px 在 3.5 倍屏上需要 **490 物理像素** —— 326 要被放大 1.5 倍。

新上限与取舍：

| 参数 | 旧 | 新 | 理由 |
| --- | --- | --- | --- |
| maxEdge | 2048 | **4096** | 现代 WebView 的 2D 画布上限普遍 ≥4096 |
| maxCellHeight | 480 | **720** | 显示高度上限 320px × 3.5 倍 = 1120，取一个折中 |

## 三、顺带修掉的三件事

- **导入图片会二次有损压缩，还会把动图拍成静态图**：`canvas.drawImage` 只画得出第一帧。
  现在 `shouldKeepOriginal()` 先判断：≤3MB 且 ≤400 万像素（动图 150 万）就**原样搬进资产库**。
  真要压时长边从 1024 提到 1536。

# 逐帧图定位：一次「位置没错、内容全空」的错（v0.15.4）

你报了两轮「一闪一闪、大部分时间不显示」。第一轮我修的是**帧数**（网格 16 格只画了 9 帧，

**每一帧的定位本身就是错的**。

## 一、根因：`background-position` 的百分比语义

原来的精灵动画是这样写的：

```css
.mascot-sprite {
  width: <一格宽>; height: <一格高>;
  background-image: url(<整张雪碧图>);
  background-size: 800% 200%;                 /* 8 列 2 行 */
  background-position: -100% 0%;              /* 以为「往左推一格」 */
}
```

`background-position` 的百分比不是「容器尺寸的百分之多少」，而是：

```
位移 = 百分比 × (背景定位区尺寸 − 背景图尺寸)
```

背景图被 `background-size: 800%` 放大成了 8 倍容器宽，于是：

```
-100% → (-1) × (W − 8W) = +7W      ← 正数，把图推到容器右边外面
```

结果：**只有第 0 帧（0%）落在容器里，其余帧容器里什么都没有。**
8×2 的网格里角色只出现 1/16 的时间，9 帧的网格里 1/9 —— 也就是「每圈闪一下」。

## 二、为什么前面几轮都没查出来

因为这个错误**同时躲过了三类检查**：

| 检查手段 | 为什么漏掉 |
| --- | --- |
| 读代码 | `-col*100%` 太像「标准精灵图写法」了（网上教程确实有这种写法，只是它们配的是**像素**偏移）|
| 量元素几何 | 元素尺寸、位置、层级全对 —— 错的是**背景画在哪**，不是盒子在哪 |
| `?framecheck=1`（上一版加的） | 它拿 `getComputedStyle().backgroundPosition` 反推格号，**用的是和渲染同一套错误假设**，等于自己证明自己 |

第三行是这篇最该记住的一条：**自检如果复用了被测代码的假设，它就只能证明「代码和自己一致」。**
这次的检查全部改成从**真实几何 / 真实像素**出发：

- `?framecheck=1`：用 `(容器.left − 整图.left) / 一格宽` 反推露出来的是哪一格，与 `data-frame` 对比；
- `?frame=N`：把第 N 帧冻住，**逐帧截图数像素**。

## 三、修法：改用像素平移，并把规则钉死

```tsx
<div class="mascot-sheet" style="width: cellW; height: rowH; overflow: hidden">
  <img class="mascot-sheet-img" style="width: cellW*cols; height: rowH*rows"
       src="..." transform="translate3d(-col*cellW, -row*rowH, 0)">
</div>
```

- **没有任何百分比**，位移就是像素；
- 换帧是合成层变换，**不触发重绘**（以前每换一帧重绘一次背景层，手机上本来就容易掉帧）；
- 位移算法抽成 `src/mascot/sheet.ts` 的 `cellOffset` / `sheetTranslate`，8 条单测钉死：
  每一帧都落在网格内、互不重复、按行列推进、脏数据不崩。

顺带修的两处，都是这一轮我自己写出来的：

1. `Math.max(1, frame)` 这种「防 NaN」的夹取把**第 0 帧也夹成了 1**（第 0 帧与第 1 帧映到同一格）；
2. `-0` 会拼成 `-0px`，归一成 `0`。

两条都是写完单测立刻抓出来的 —— 这正是把位移抽成纯函数的价值。

## 四、帧率：`setInterval` → `rAF` + 时间累加

你说「疑似帧率不对」有道理，但来源有两层：

1. 上面那个 bug：每圈只出现一帧 → 看起来像卡顿 / 闪烁；
2. `setInterval(…, 1000/fps)` 按**排队次数**走：主线程一忙（课表渲染、提醒调度、
   资产解码都在同一个线程），回调积压，恢复时连触发好几次 → 「卡一下然后猛跳几帧」。

现在用 `requestAnimationFrame` + 时间累加：按**真实经过的时间**算该显示第几帧，
忙的时候自动少跳（`MAX_CATCHUP = 1`），永远不积压。

> 注意：无头浏览器 + `--virtual-time-budget` 下 rAF 基本不推进（虚拟时钟只推定时器），
> 所以这类验证必须**实时跑**：启动浏览器、等 12 秒、从信标里读结论。
> 虚拟时间下测出来的 `visited=1` 是环境假象，不是应用的问题。

# 角色设置也纳入外观锁定（v0.15.6）

你的一句「角色设置也要放误触」，指向的是一个**机制漏洞**，不是新功能。

## 一、漏在哪

外观锁定的实现是一条 CSS 选择器列表：

```css
.studio.locked .panel button,
.studio.locked .panel input,
.studio.locked .panel select,
.studio.locked .panel .switch,
.studio.locked .panel .swatch,
.studio.locked .panel .preset-card,
.studio.locked .panel .wp-item,
.studio.locked .panel .upload-zone,
.studio.locked .panel .segmented { pointer-events: none; }
```

它覆盖了"控件"，但**没覆盖"可点行"**。而「角色」面板里几乎每件事都是可点行：

```
导入角色包 · 更多功能 · 做一个角色 · 用一张图或一段视频 · 粘贴角色包内容
导出角色包 · 检查这个角色 · 放回默认位置 · 使用说明书 · 移除角色
```

全项目 `list-row tap` 一共 28 处：`SettingsView` 18 处（设置页，不受外观锁定管）、
`MascotPanel` 10 处 —— **外观页里只有角色面板在用这个模式**，所以漏洞正好只落在它身上。
用户看到的现象就是：外观锁着，角色那一整块照样能点，其中「移除角色」还会连带清素材。

## 二、为什么原来还特意豁免过它

代码里留着一句注释（v0.12.0 写的）：

> 角色面板是例外：导入/移除角色包是**数据操作**，不是调样式。
> 外观锁定是为了防手滑改坏配色，不该拦住"第一次把角色放进来"这一步。

这个理由本身没错，但它把"导入"和"移除 / 替换 / 移动"混在一起豁免了 ——
后三个明明都是能一键改掉已有角色的操作。

所以这一版的做法是**把例外收窄到真正需要的那一种情况**：

```tsx
const locked = s.prefs.studioLocked !== false && !!pack;
```

有角色 → 整块只读；还没有角色 → 放行（那时唯一的动作就是第一次把它放进来）。
CSS 侧对应一条：`.panel .mascot-rows.unlocked .list-row.tap { pointer-events: auto; }` ——
与禁用规则**同权重、后出现**，因此稳定生效，不需要靠 `!important` 打架。

## 三、另外两处防误触

1. **面板里的锁定提示条**。原来只有顶部那条 `position: sticky` 的锁定栏；
   外观页面板很多，滚到角色那一段时它早就不在视野里了 ——
   **"锁住了却找不到钥匙"比不锁更糟**。现在角色面板上方有一条同款提示，自带「解锁」按钮。
   它渲染在 `Panel` **外面**：`.studio.locked .panel button` 会把面板内所有按钮禁用，
   提示条自己要是也在里面，那个解锁按钮就点不动了。
2. **「移除角色」二次确认**。它不可逆（素材一并从本机清掉），现在走应用统一的
   `confirmDanger`（设置 → 防误触里可以关掉"危险操作二次确认"）。

## 四、把这类漏洞变成可测的量

自检新增一项 `LOCK`：数一遍"外观锁定时**仍然能点**的面板控件"，以及"解锁入口有几个、能不能按"。

| 场景 | 锁定时仍可点的面板控件 | 解锁入口 |
| --- | --- | --- |
| 有角色（`?mascot=4`） | **0** ✓ | 2 个，都可用 ✓ |
| 没有角色 | 2（导入角色包 / 更多功能，故意放行）✓ | 1 个，可用 ✓ |

这一项的价值不在这次，而在下次：以后任何人往面板里加一个"可点行"而忘了加进锁定列表，
自检立刻从 0 变成 1。**一个"锁了但没锁全"的机制，光看是看不出来的。**

# 角色状态机的两层化：从"节拍器"到"像活的"（v1.1.0）

## 一、原来的设计，以及它为什么会被看穿

```
相位：idle / react / sleep / drag          —— 由用户操作与时间决定，语义稳定
idle 里的动效：mascotBreathe 5.2s + mascotBob 6.8s，两条 infinite 动画
眨眼：blinkDelay(seed)，seed 每次 +1.37
```

问题不在"动作少"，而在**它们是确定的**：

1. 两条正弦永远同相位、同幅度、同周期 —— 看三秒就知道在循环；
2. 眨眼那套"随机"是假随机：`blinkDelay(seed)` 是纯函数，seed 每次固定 +1.37，
   于是**每个用户、每次启动的眨眼节奏完全一样** —— 想做随机却做出了确定性，是最讽刺的一种；
3. react 永远是同一段 900ms，点第三次就没新鲜感；
4. 400ms 轮询推进：所有动作只能落在 400ms 的整数倍上，空闲时也在空转耗电。

## 二、两层结构

| 层 | 内容 | 谁决定 |
| --- | --- | --- |
| 相位 | idle / react / sleep / drag | 用户操作 + 时间（**不随机**）|
| 微动作 | 呼吸 / 抖一下 / 伸展 / 抬头 / 打哈欠 | 当场掷：做什么、做多久、快慢幅度 |
| 反应 | hop / sway / startle / peek | 点一下时掷 |

关键取舍：**相位不随机**。"用户在拖"和"它在打哈欠"是两种性质的事，混在一起就没法推理；
随机只发生在内层。

## 三、随机数注入：状态机里没有一处 Math.random

```ts
export type Rng = () => number;
export function advance(rt, now, dragging, opts?: { energy?, rng?, sleepAfterMs? })
```

生产传 `Math.random`，测试传固定种子的线性同余。收益三条：

- 状态机仍是纯函数 → 同一个种子 + 同一串时间戳 = 完全相同的动作序列，可单测、可复现；
- "偶尔卡在某个动作不动"这类问题能二分定位；
- 不会出现"本地过一次、CI 挂一次"的随机失败。

## 四、"不会连着两次做同一个动作"是硬保证，不是降权

第一版只给"刚做过的动作"降权（×0.15），单测跑 300 轮就复现了连续重复 ——
而**连续两次一样的动作正是"假随机"最容易露馅的地方**（人眼对重复极度敏感）。
现在掷到重复就重掷一次：多一次随机调用，换一条能断言死的硬规则。

## 五、能量：让"性格"从可见变成可感

```ts
energyOf({ hour, minutesToClass, idleForMs, interactions }) → 0..1
```

临近上课 +0.25、白天 +0.08~0.15、午后 −0.15、深夜 −0.35、久无人理 −0.15/−0.25、
刚被点过每次 +0.06（上限 +0.24）。它只改内层权重与动作乘数：

| 能量 | 抖一下的权重 | 打哈欠的权重 |
| --- | --- | --- |
| 0.95 | 0.5 + 0.95×2.2 = **2.59** | 0.25 + 0.05×2.4 = **0.37** |
| 0.05 | 0.5 + 0.05×2.2 = **0.61** | 0.25 + 0.95×2.4 = **2.53** |

实测（同一套代码，只差"有没有被点"）：安静待机 60 秒 `breathe×4 yawn×3 perk×4 stretch×1 fidget×3`；
被点 8 次之后 45 秒 `fidget×10 yawn×6 perk×6 breathe×4` —— 同一个角色，两副脾气。

## 六、反应：四种变体，且与素材形态无关

以前"点一下有反应"只对**有 react 素材**的角色成立；用视频做的逐帧图角色点下去画面纹丝不动。
现在反应是**一次性 CSS 动画**（只动 transform / opacity），任何素材都看得见：

```css
.mascot-inner.rx-hop { animation: mascotRxHop 520ms var(--ease); }       /* 蹦一下 */
.mascot-inner.rx-sway { animation: mascotRxSway 700ms var(--ease); }     /* 晃两下 */
.mascot-inner.rx-startle { animation: mascotRxStartle 420ms var(--ease); } /* 被吓一跳 */
.mascot-inner.rx-peek { animation: mascotRxPeek 460ms var(--ease); }     /* 凑过来看 */
```

**一个必须记下来的实现细节**：同类反应连着两次时，React 认为 `className` 没变，
CSS 动画**不会重播**（第二次点下去毫无反应）。所以 `MascotArt` 里用命令式重启动画：
摘掉类名 → 读一次 `offsetWidth` 强制重排 → 加回类名。

## 七、轮询改成排程

```ts
const wake = nextWakeAt(next, { sleepAfterMs });   // 下一个该变化的时刻
timer = window.setTimeout(step, Math.max(120, wake - Date.now()));
```

`nextWakeAt` 取"当前微动作结束 / 反应结束 / 睡点"三者中最早的一个；
睡着之后不再排睡点（否则会一直空转）。既省电，也让动作节奏不再被 400ms 网格量化。

## 八、把"随机感"变成可测的量

新增 `?behavecheck=秒数`（每 200ms 读 `data-behavior` / `data-reaction`，记录**切换序列**）
与 `?poke=N`（让它自己每 4 秒被点一下 —— 无头浏览器里点不动它，没有这个入口反应路径就永远没验证过）。

| 场景 | 结果 |
| --- | --- |
| 60 秒安静待机 | 动作种类 **5**、切换 14 次、最长同动作 12.2s、序列无相邻重复 |
| 45 秒 + 8 次点击 | 反应 **8** 次、四种都出现（`sway peek startle hop peek startle hop peek`）、无相邻重复 |

## 九、跑测试时顺带抓到一个真 bug

`widget.test.ts` 红了两条。不是测试写错，是产品 bug：

```ts
const today = todayISO();   // ← 真实的今天，而不是传入的 now
```

`buildWidgetPayload(data, now)` 忽略了 `now` 来做"今天"那一栏。影响：

- 调用方传别的时刻时，"今天"算的是真实当天（小组件若预渲染第二天就会错）；
- 那几条测试**只在工作日碰巧通过** —— 它断言的其实不是它以为的那件事，一到周六就红。

改成 `toISODate(now)`，并补了一条回归测试：同一时刻往前推一天，`today` 的内容必须完全不同。

## 七、产品化过程中揪出的两个"只有对着用户才看得见"的缺陷

这两个都不是本次改动引入的，是**为了公开而逐条读文案**时才浮出来的：

1. **更新日志里显示裸星号**。条目正文用 `**` 标重点（15 条用到），而 `ChangelogSheet`
   直接把字符串塞进 DOM —— 用户看到的是 `**真实帧数**` 而不是**加粗的真实帧数**。
   改法：加一个 `renderText()` 把奇数段包成 `<b>`。
2. **说明书里同样的问题**，11 处。改法更彻底：说明书的正文组件（P / UL / Steps / Note / QA）
   统一过一遍 `rich()`，写文档时照旧用 `**`，渲染时统一转换。

——这类问题的特点是"写的时候满屏都是 `**`，根本看不出来"，只能靠渲染后检查。



## 八、网页版：把"能不能搬"变成一条判据

这一版把前端发布到了 GitHub Pages。做之前先回答的是"哪些功能可以迁移、哪些必须删掉"，
而这个问题不该靠感觉回答 —— 判据只有一条：**这项能力是不是依赖只有原生壳才有的系统能力**。

### 1. 判据落地后的三张清单

| 类别 | 内容 | 处理 |
| --- | --- | --- |
| 纯计算 / 纯界面 / 自带编码管线 | 时间引擎、本周 / 今日 / 任务 / 出勤 / 搜索、Excel / CSV 导入（自写 ZIP + `DecompressionStream`）、ICS / CSV / Markdown / 长图 / JSON / 主题包 / 角色包 / 分享码、外观 DIY、角色（视频抽帧、走动、翻面、快捷菜单）、声明式插件、说明书 | 原样可用 |
| 已有网页实现的平台层 | `WebNotifier`（页面内定时器 + 通知）、`saveTextFile` 的 `webDownload()` 分支、`initStorage()` 的 localStorage 后备 | 接进界面并如实说明 |
| 系统能力 | 桌面小组件（RemoteViews）、电池优化 / 自启动 / 精确闹钟授权、8 项真机检查 | 删掉面板，换成说明 |

值得记一笔的是：`WebNotifier`、`webDownload()`、localStorage 后备**早就在**（0.9.x 就在平台层里留着），
数量上约占网页版可用功能的一半 —— 这次主要是把它们接出来、并且把"网页版的边界"写进用户看得见的地方。

### 2. 产品化里最容易被忽略的一步：不让网页版继承 Android 的承诺

"息屏也会提醒""关掉应用照样响"在网页版是假话。这类句子留在界面上，用户会信，然后错过一节课再卸载。
所以凡是与平台有关的说法一律按 `isNativePlatform()` 分支，改到的位置：

| 位置 | Android | 网页版 |
| --- | --- | --- |
| 首次启动第四条 | 提醒交给系统闹钟 | 提醒需要页面保持打开（并给出装 Android 版的理由） |
| 设置 → 提醒通道 | 精确闹钟行 + 已排入通知系统 | 不渲染精确闹钟行；排程注明"页面内的定时器，关掉页面即失效" |
| 设置 → 后台提醒可靠性 | 电池优化 / 自启动 / 系统设置入口 | 整块换成 `WebReminderPanel`「网页版的提醒边界」 |
| 设置 → 桌面小组件 | 添加路径 + 立即同步 | "为什么没有" + 构建注入的 Android 版入口 |
| 提醒可靠性检查 | 8 项 + 电池 / 厂商字段的报告 | 3 项 + 浏览器环境的报告 |
| 说明书 | 必须放行的四项 | 四条边界；FAQ 四问各有一份网页版答案；存储章节写 5 MB 配额 |
| 更新日志顶部 | 无 | "历史里这几类属于 Android 版"（记录不改写，但读者要知道） |

### 3. 发布：相对路径 + 构建注入的小设计

- `base` 从默认改成 `'./'`。项目页在 `/<repo>/` 子路径下，绝对路径会白屏；相对路径同时适配子路径、自定义域名与 Capacitor 的 `https://localhost/`，**一份产物两个宿主**。
- 网页版需要"去哪装 Android 版"的入口，但地址不能猜。做法是构建时注入：Actions 自带 `GITHUB_REPOSITORY` → `vite.config.ts` 折成 `__REPO_URL__` → `src/app/meta.ts` 暴露 `ANDROID_RELEASE_URL`；为空时所有入口自动隐藏。
- `.github/workflows/web.yml`：`npm ci` → `npm test` → `npm run build` → `deploy-pages`，单测不过不发布。

### 4. 验证：静态检查看不出"渲染的是哪一支"

平台分支是运行时决定的，`grep` 只能证明两条分支都写在了源码里，证明不了用户看到的是哪一条。
所以在自检里加了两个口子：

1. `PLATFORM` 指标 —— 产物自己报它认为跑在哪个平台；
2. `?diag=1&text=<选择器>` —— 把匹配元素的**渲染后文字**经图片信标回传。

验证方式是把 `dist/` 挂到 `/repo/` 前缀下（真正模拟 Pages 子路径），用无头 Edge 跑：

| 检查 | 结果 |
| --- | --- |
| 子路径资源 | `/repo/` 200、`/repo/assets/…` 200、`index.html` 里是 `./assets/…` |
| 320 / 360 / 390 | `OVERFLOW 0`、`SMALL_TAP 0`、`OVERFLOW_Y 0`、`MARKDOWN 0`、`ROOT ok(18849)`、标签栏 5 项全在框内 |
| `PLATFORM` | `web`（三宽度与单页运行都是） |

## 九、电脑适配与下载页（v1.5.0）

这一版只做两件事，都发生在「外壳」层：网页版在电脑上真正变成桌面布局；「去哪装 App」变成一条路径。

### 1. 判断条件为什么不放在 CSS 里

同一份代码在 Android 壳里跑，平板横屏同样超过 1024px，而那种情况必须保留底部标签栏。

| | 手机 | 电脑 |
| --- | --- | --- |

### 2. 两个只有量了才知道的坑

**分列加错了层**。第一版把 `columns` 写在 `.content-inner.two-col` 上，

外层只有一个子元素，那个子元素自己就是一列，于是永远只有一列。改成 `> *` 之后：
`panels=17 cols=2`（设置）、`panels=9 cols=2`（外观）。

**弹层动画必须关掉**。`sheetUp` 是「从下往上 4%」，居中之后再用它，
开场那一帧会把对话框推到画面外（`transform` 被动画覆盖）。所以 `.app.wide .sheet` 里写了 `animation: none`。

### 3. 新增 `DESKTOP` 自检行

宽屏样式整块挂在 `.app.wide` 下，看截图分不出「样式没生效」和「元素本来就在那儿」。

没命中时输出 `DESKTOP off`，手机端就该是这一行。

实测：1280/1440/1920 下 `nav=236x…@0,0`、`content=…@236,0`、

### 4. 下载页

`public/download/index.html` —— 静态页，不经过 React，发布到 `/download/`。
为什么单独做一页：同学拿到的是一个链接，这一页要立刻给出安装包与安装步骤，

## 十、可选云备份：Supabase + Resend（v1.6.0）

这是第一个**会联网**的功能。所以这一节的重点不是「怎么接」，而是「怎么保证不接的时候什么都没变」。

### 1. 先定死性质，再写代码

| 性质 | 怎么保证 |
| --- | --- |
| 没配置就完全离线 | 构建期注入，两项为空时 `cloudConfigured()` 为假：面板不渲染、client 在入口直接抛错；单测断言「一个请求都不发」 |
| 打开应用不联网 | 所有网络调用都挂在用户动作上；实测：把 `VITE_SUPABASE_URL` 指向本地服务，打开设置页并静置 6 秒，服务端日志里 0 条请求 |
| 点按钮才联网 | 正对照：填表点「登录」后日志里出现且只出现一条 `MISS /fakesb/auth/v1/token` |
| 读不到别人的数据 | 数据库行级安全 + 真项目实测（见第 6 节） |

### 2. 服务端：两张表，四条策略，一条都不多

`supabase/schema.sql` 是幂等的：

- `timetables`：主键 `user_id` → `auth.users(id)`（一人一行），`payload jsonb` 存那份导出的 JSON；
  四条策略分别对应读 / 写 / 改 / 删，条件全是 `auth.uid() = user_id`；
- `mail_log`：发信记账，**故意不建策略**并 `revoke` 掉 `anon, authenticated` —— 只有 service_role 能碰；
- 体积上限用 `pg_column_size(payload) < 1048576` 兜一道，客户端已经先算过字节；
- `updated_at` 由触发器维护（客户端时钟不可信）。

### 3. 客户端：不引入 SDK

为了「登录 + 读写一张表」而装 `@supabase/supabase-js`（几百 KB）与本项目的依赖立场不符 ——
运行时依赖到现在仍然只有 React 与 Capacitor。所以 `src/cloud/client.ts` 直接对着 HTTP 接口写，
顺带做了三件小事：20 秒超时、`AbortController` 取消、把 Supabase 的英文报错翻成人话。

翻译这件事有个真实的教训：本地假服务器回 `404` + 正文 `no` 时，界面就真的显示了一个 `no`。
改成「只有像句子的原文才原样显示」，其余按状态码给一句能照着做的话（`404` →「接口地址不对」）。

### 4. 备份的边界（写进界面，也写进测试）

字节数用 `TextEncoder` 精确算，**不能拿 `length` 顶替** —— 一份全中文的课表，`length` 会低估约三倍。
自引用还带来一个小坑：第一次量的时候 `stats.bytes` 是 `0`（一位数字），写回去变成四位数，
于是记录的值比真实值少 3 字节 —— 单测直接把这个差值抓了出来（`expected 5906 to be 5909`），改成量两次才对。

偏好走白名单：`reminderOffsets / dailyBrief / briefHour / confirmDestructive / studioLocked`。
将来新增的本地设置不会自动跟着上云 —— 这比「记得手动排除」可靠。
角色包不进备份（有自己的文件格式，体积大），界面与说明书都写明了。

### 5. Edge Function：两个，安全性质由测试守着

| 函数 | 关键性质 |
| --- | --- |
| `delete-account` | 身份只从 token 查（`/auth/v1/user`），不接受客户端传 user id；用 service_role 删数据与账号 |
| `send-mail` | **不读 `body.to`**，收件人只来自 token；每小时 5 封 / 每天 20 封；key 只从环境变量读 |

## 十一、角色更像活的 + 云端角色加载提速（v1.8.3）

### 1. 问题一：久等之后角色"卡"在同一个动画上

用户的原话是"等待若干分钟后不要一直显示一种动画"。翻回状态机看，根因在外层相位：
`sleep` 一旦进入就锁死，内层微动作虽然在掷，但素材固定是"睡觉那一张"、
动作幅度又被整体压慢压小（快慢 ×1.6、幅度 ×0.75）—— 搁在桌上几分钟看过去就是卡住了。

改法是给睡眠加一层**打盹循环**（`MascotRuntime` 多两个字段 `stirUntil` / `nextStirAt`）：

| | 之前 | 现在 |
| --- | --- | --- |
| 睡着之后 | 一直睡着 | 每隔 45–150 秒醒一小段（4–14 秒）|
| 那一小段 | —— | 走**正常**动作池（含走动），结束时打个哈欠睡回去 |
| 相位轨迹 | `idle → sleep` 然后不动 | `idle → sleep → idle → sleep → …` |

两个必须做对的细节，写在这里免得以后被"优化"掉：

1. **半醒要抬精神头**。`energyOf` 会因为"十几分钟没人理"把能量压到 0.2 上下，
   而"走走"的权重曲线在 e=0.7 附近取峰值、低能量时几乎为 0 —— 不兜底的话，
   醒了也只会挑最蔫的动作，等于没醒。所以半醒那一段用 `WAKING_ENERGY = 0.62` 兜底。
2. **睡着时"走走"仍然是 0**。动作池分两套：`behaviorWeights(energy, recent, { dozing: true })`
   是睡眠池（翻身 / 打哈欠 / 慢呼吸），醒着那套才是完整八种。
   旧单测里那条"睡着之后不会踱步"没有被删掉，而是**改写成更准的判据**：
   睡着的那一刻不许出现走动，半醒那一段可以。

顺带把动作池从 6 种扩到 8 种（新增 `look` 东张西望、`nod` 点头），
并给三条动画通道各加一个配比（`ChannelMix`）：张望偏左右摆、点头偏上下浮。
没有配比的动作仍是 1:1:1，与之前逐位一致 —— 这条有单测钉住。

还加了**自发小动作**：没人点也会按概率播一次一次性动画（醒着 0.28 / 睡着 0.22），
池子只有 hop / sway / peek，`startle`（被吓一跳）不参与 —— 没人惹它就播那个，看起来像 bug。

### 2. 问题二：加载云端角色很卡

"很卡"是四件事叠在一起，拆开各自都不难：

| 原因 | 量级 | 改法 |
| --- | --- | --- |
| 打开面板串行四次往返（列表 → profiles → 数行数）| 每次几百 ms | 列表与配额 `Promise.all`；`myQuota` 内部也并行 → 一次往返 |
| 两个入口各拉一次（`openCloudSheet` + 面板挂载）| 请求翻倍 | 模块级 in-flight 去重 + 60 秒缓存（「刷新」用 `force`）|
| 面板里同步序列化整包只为显示"多大" | 几 MB 的 `JSON.stringify` | `estimateMascotBytes`：只做加法，口径与真值对齐 |
| 用别人的角色时白转两趟（对象 → stringify → parse）| 8 MB 的包两趟 | `fetchMascot` 收到对象直接校验；`importMascotPackObject` 直接装 |

再加上三处体验修补：忙的时候说清在忙什么（`mascotsBusy` → `mascotsStage`，
按钮上写「下载中」「保存中」）、存盘前让出一帧（`nextPaint`，否则"保存中"根本没机会画出来）、
素材预热改成一图一次空闲回调（`src/mascot/prewarm.ts`）。

### 3. 网页版的落盘：一次导入写一次

网页版没有 SQLite，素材走 localStorage 后备，而 `lsSave` 是**整表重写**。
导入一个角色是连着四次 `putAsset` —— 同一份几 MB 的字符串被拼四遍、写四遍。
改成本轮合并成一次（`lsSaveSoon`），并在 `pagehide` / 转后台时立刻补写：
"晚一个宏任务"不能变成"丢数据"，这一条有单测（`src/storage/batch.test.ts`）。

### 4. 验证

| 项 | 结果 |
| --- | --- |
| 打盹循环（`?mascot=6&doze=6&behavecheck=75`）| 睡 **5** 次 / 半醒 **4** 轮；相位序列 `idle→sleep→idle→…`；半醒采样 62/375 |
| 半醒那一段的动作 | 分布含 walk / look / perk / fidget —— 是醒着那套池子 |

### 1. 设置页：从"十几块平铺"到"四块 + 收起"

## 十三、角色：走动的速度，与「少一些自己的简易动画」（v1.9.1）

两条反馈：「步子迈了半天还是基本在原地」「变化多基于给定动画，少一些自己的简易动画，尤其是左右摇摆这种」。

### 1. 走动为什么几乎没动

`planWalkStep` 原来把**距离**与**时长**当成两个独立的随机数：
走 24–72px、花 11–20 秒。而 walk 这个微动作的窗口只有 5–9 秒 ——
每一趟都在半路被打断，读回实际位置当下一次起点。有效速度只剩 **2–4 px/s**。

改法：给**速度**，时长由距离算出来（并且夹在动作窗口内），动作窗口放宽到 4.5–10 秒。

| | 之前 | 现在 |
| --- | --- | --- |
| 名义一步 | 24–72px / 11–20s | 34–72px，速度 9–14 px/s |
| 实际生效 | 约 10–30px（被打断）| 34–72px（走完）|
| 100 秒实测（`?mascot=6&behavecheck=100`）| 锚点范围 **11px** | 里程 **126px**、范围 89px |
| 有 `walk` 素材时 | 权重不变 | 权重 ×2.2（`AdvanceOpts.walkBias`）|

### 2. 自己的简易动画：让位给素材

| | 之前 | 现在 |
| --- | --- | --- |
| 被点一下 | `react` 素材 **与** 程序化 `rx-*` 叠着播 | 有素材只播素材（≥0.9s），没有才用 `rx-*`（`reactionIsAsset` 让渲染层完全让位）|
| 自己动一下 | 0.28，池子 hop/sway/peek | 0.14（有 react 素材 0.3），池子 hop/peek |
| 「东张西望」微动作 | 慢而大的左右摆 | **删除** |
| 「晃两下」反应 | rotate ±4.5° | **删除** |
| sway 通道 | 随行为幅度放大（最高 ×1.85）| **只减不增**：`Math.min(1, amp × mix.sway)` |

自检里新增两个量把这两件事变成可读的数字：**走动里程**、**反应来源: 素材N/程序M**。
实测：`?mascot=1`（自带 react 素材）18 次反应全是素材；`?mascot=6`（无 react 素材）4 次全是程序化
—— 优先级正确、回退也正确。

## 十四、三处「看不见的失败」（v1.9.2）

三条用户反馈，背后是三个**在构建日志与自检里都看不出痕迹**的问题。

### 1. 安卓版没有云端入口：构建变量漏了一个工作流

`cloudConfigured()` 读的是构建时注入的 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`。
`web.yml` 有、`android.yml` **没有** —— APK 里的 Web 产物云配置为空，
云备份 / 云端角色 / 右上角云图标整块不渲染。构建照样成功、签名照样通过、单测全绿。

修法：补 env + **打包后核对产物正文**（查得到云端域名才算过，否则 `::error::` 让这一步失败）。
教训：**「某个功能整块消失」这类事故必须有一条会失败的检查**，而不是日志里一行 warning。

### 2. 桌面小组件：没人叫它重画

小组件活在桌面进程里，`updatePeriodMillis=0`，所以只在应用推送时刷新。
上午那节课上完之后桌面还显示着它 —— 不是数据错，是**没人叫它重画**。

| | 之前 | 现在 |
| --- | --- | --- |
| 数据 | 今天剩下的课 + 一节「下一节」（推送时定死）| 再加 `upcoming`（最多 6 节，带绝对毫秒与日期）|
| 选哪一节 | 推送时决定 | 渲染时按 `endMs > now` 现挑（纯线性比较，不推算时间）|
| 重画时机 | 只有推送 | 加闹钟：下一节开始 / 这节下课 / 跨天零点（`WidgetRefresh` + `WidgetRefreshReceiver`）|
| 推送保证 | 挂在提醒排程末尾（出错就跳过）| 排程里必定执行 + 课表一变独立推一次 |
| 过期数据 | 几天前的课当「今天」| 比对 `todayIso`，过期改显示「接下来的几节课」|

自检 `?widgetcheck=1` 把推过去的数据与下次自刷新时刻打出来，两个进程之间的问题一眼定位。

### 3. 角色的自然状态：从七种收敛成三个

「点击动画不要自然触发，自然状态就在走路、待机与休息三个状态里切换」——
于是删掉自发小动作、删掉五种自己编的微动作，睡着的哈欠也去掉：
自然状态只剩**待机（breathe）/ 走路（walk）/ 休息（sleep 相位）**。
保留打盹循环、走动速度与权重、素材优先（有 `react` 素材就播素材、有 `walk` 素材就更常走）。

## 十五、撤销为什么难用，以及怎么改成「可逆」（v1.9.4）

原话：**「撤销等操作非常奇怪（用的难受，感觉很鸡肋，尤其是撤销读取云端数据。这个云端-本地的数据结构与操作方式可能还要优化），能不能优化一下？或者，直接保证所有操作是可逆的是否可行？我注意到特殊原因编辑课表（调课/停课）之后无法便捷的恢复，这个也要思考一下怎么改。」**

### 1. 三个病灶，都不是「撤销按钮不好看」

| 现象 | 真实原因 |
| --- | --- |
| 撤销「读取云端数据」之后更奇怪 | 快照里**只有课表数据**，没有外观与偏好。云端恢复是「整份文档」替换，撤销却只换回了 data —— 于是课表退回去了、主题还是云端那份，看起来像**还原了一半** |
| 感觉鸡肋 | 只有「上一步」能撤。提示条 4 秒后消失，之后再想撤就没入口；提示条说的还是「上一步」而不是「你刚才做的那一步」 |
| 调课 / 停课之后恢复不了 | 覆盖（override）在数据模型里是「给这次课加一条调整」，不是「改课表」。面板里已存在的调整**列在最底下**、按钮叫「删除」，用户根本看不出那是「恢复原样」 |

### 2. 数据结构：快照从「只存课表」升级成「整份文档」

```ts
interface ChangeSnapshot { data: AppData; theme: ThemeState; prefs?: PrefsState }
interface ChangeSet { id; label; source; at; before; after; coalesceKey? }
```

- `setData(data, label, source, coalesceKey?)` —— 普通编辑（before/after 都是整份快照）
- `applyDocument({data, theme, prefs?}, label, source)` —— **一次改好几样**的操作（从云端恢复、整份导入）
- `setThemeWithHistory(...)` / `patchTheme(patch, silent?, historyKey?)` —— 外观编辑也进历史，连续拖动按 `coalesceKey` 合并成一步
- 撤销/重做一律 `writeSnapshot()` 整份写回，所以「退回去」在任何时候都是**同一份状态**，不存在只退一半

**为什么云端 - 本地不做差量合并**：本地是权威副本（离线也能改），云上存的是整份快照。
恢复 = 用云那份**替换**本地整份文档，所以它的逆操作天然就是「换回本地上一整份」。
去做逐字段 diff 只会制造「有些字段没跟上」的半个状态 —— 现在的做法反而更简单、更容易讲清楚。

### 3. 入口：从「一个按钮」变成一个能看懂的系统

| 入口 | 行为 |
| --- | --- |
| 顶栏 ↶ 轻点 / ↷ 轻点 | 退一步 / 进一步（长按 600ms = 打开操作历史，不会误触发） |
| **操作历史**（新面板 `HistorySheet.tsx`）| 按时间列出最近的可撤销步骤（标签 + 时分秒），**点任意一行就退回那一步**；下面还列着可重做的步骤。注明「最多 40 步、只在本次运行内」 |
| 设置 →「防误触与撤销」 | 多一行「操作历史」，副标题显示「可撤销 N 步」 |
| 提示条 | 调课 / 停课 / 换教室 / 考勤 / 勾选任务 / 删除任务 / 导入 / 应用外观预设 / 从云端恢复 …… 都带「撤销」 |
| 调课面板顶部 | 「这门课已调整的 N 次」，每条一个**「恢复」**按钮 + 说明「点「恢复」这一次课就按原样上」 |
| 今日页 | 被调整的那一节下面直接给「恢复这一次」 |

提示条与历史面板的一致性靠 `peekUndo()`：只有**这一步仍是最后一步**时才提供撤销，
否则如实提示撤不回去了 —— 宁可说不，也不悄悄撤错东西。

### 4. 可逆性的边界（诚实清单）

全部可逆：课表增删改、调课 / 停课 / 换教室、考勤、任务、导入（课表 / 日历 / 表格）、
外观（主题 / 主色 / 圆角 / 模糊 / 字号 / 壁纸）。

**边界说准**：设置里的开关（提醒开关、防误触开关这类）**本身不进历史** —— 再点一次就回去了，
把每次拨动都记一笔只会把撤销栈塞满。但「从云端恢复」「导入备份」这类**整份文档级**的操作
会把偏好一起记进那一笔，撤销时课表、外观、偏好一起退回。

**不可逆**（在说明书里同样写明）：删除云端备份、注销账号、把角色上传到云端（这是一次分享行为）、卸载应用或清除应用数据。

### 5. 验证

- `src/app/history.test.ts` 9 个：栈语义、40 步上限、连续同类合并、`briefs` 里**不含快照**（防止面板把整份文档拖进内存）
- `src/app/store.undo.test.ts` 新增 4 个：主题撤销 / 重做、`applyDocument` 把课表 + 外观 + 偏好一起退回、
  只改课表时不会动主题、`historyEntries` / `undoTo` / `redoEntries`
- 无头浏览器扫 320 / 360 / 390 三档：新面板与新按钮无横向溢出、触控目标达标

### 6. 补丁 v1.9.5：三处「够不着」的地方

1.9.4 的包发出去之后，又发现两个真问题（都在安装包里的代码里，不是网页独有的），加上布局自检报出的一处：

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 停课的课在今日页**完全看不到**，想恢复只能回周视图找那门课 | 引擎把停课的那一节从当天直接去掉（这是对的），但"停错了"恰恰要从这里改回来 | 今日页在时间线下面单列「今天被停课的 N 节」，给出节次 / 原因 / **恢复** |
| **调课到别的日子**之后，那一节下面没有「恢复这一次」 | 1.9.4 按 `(sessionId, date)` 反查调整记录，而补课那天的"出现日期 ≠ 原日期"，反查必然落空 | 改用事件自带的 `modifiedBy`（引擎填的就是 override 的 id），两种情况都有按钮 |
| 提示条上的「撤销」按钮只有 42×23 | 它是 3px/10px 内边距的纯文字按钮，比应用里最小一档按钮（46×30）还小 | 按小按钮规格重做：`min-height: 32px`、横向 14px 内边距；自检 `SMALL_TAP` 归零 |

**为什么升版本号而不是重发 1.9.4**：1.9.4 的安装包已经由 CI 从 tag 构建并发布过（9,690,743 字节，SHA-256 `61CC1711…`）。
把同一个 tag 指到新的 commit，就会出现"一个版本号对应两个不同的包"—— 这件事在 1.4.x 上翻过一次车，
所以按规矩走 1.9.5。

**自检也跟着补了一条**：`?ovcheck=1` 原来只验调整面板；现在它跑两阶段，第二阶段在**今天本来没有课时临时造一节**
（否则周末跑这个自检永远只是"跳过"，等于没验），验完立刻把临时课与它的调整记录删掉。

## 十六、角色中心 · 拖动改课 · 小组件按尺寸排版 · 插件扩展点（v1.9.6）

四条反馈，四条独立的工作线；下面按"问题 → 改法 → 怎么验"记。

### 1. 插件系统：审查结论与落地

**结论**：在这之前它不是"插件系统"，而是**一张导出格式的参数表**。逐条核过：不能注册界面、不能监听事件、
不能改课表、不能发提醒、不能联网、没有自己的持久化、不能注册快捷键；清单里没有 `apiVersion`、没有依赖、没有配置项 schema。
唯一运行时执行点是 `runPluginExport`（store.ts），插件拿不到任何可调用对象。

**三个真缺陷**（都在界面上能感觉到）：

| 缺陷 | 为什么是问题 | 修法 |
| --- | --- | --- |
| `PluginsPanel.tsx` 的"干跑"调的是 `installPlugin(text, [])` | 它**已经写库了** —— 用户点一次，界面什么都不说，重启后多出一个插件 | 改用 `parseManifest`（纯函数）预览 |
| 安装时写死 `granted = ['read:timetable']` | 与 `types.ts`、docs/10 里"默认未授予、勾了才生效"直接矛盾；用户以为在控制权限，其实装完就放行了 | 默认不授权，提示"勾上权限才会生效" |
| `load()` 直接信任 localStorage | 安装期那 16 条校验读取时不再复查，篡改/旧版残留可以绕过 | 拆出 `validateManifest`，读取时逐条复校验，坏记录跳过并在面板告知 |

**扩展点**（零代码，仍然不执行插件代码）：

- `command` 能力：`action` 只能是 `{ kind:'export', capabilityId }`，且必须指向本插件已声明的导出能力（第二轮校验）；
  键位要过格式校验。注册进命令表时带 `plugin:` 前缀，停用 / 撤权 / 卸载即注销，键位冲突时内置优先。
- `apiVersion`（不写视为 1）与 `minAppVersion`：比宿主新的接口版本一律拒，并说明"这个插件需要更新版本的应用"。
  这条挡掉的是最难查的一类失败：装上了、但列错位、导出空表。
- 插件数据纳入本地存储体检 + 新增「清掉插件数据」入口（原来 `resetPlugins` 只有测试在调，用户既看不到也清不掉）。

### 2. 角色：三处入口合并成「角色中心」

原来和角色有关的操作散在三处：外观 → 角色里的「更多功能」折叠区（七行）、右上角云弹层里的「云端角色」、文件管理器里点开的 .json。
于是"我想换一个角色"要先猜"这件事属于哪一块"。

现在按**想干什么**分三页：换一个 / 做一个 / 分享与获取。同时补上了原本缺的一环 —— **本机角色库**：
以前"换角色"只有重新导入一条路，现在可以存最多 6 个、一键切换。

**这里有个必须记住的坑**：`applyMascot` 换角色时会按"旧包 key − 新包 key"精确回收素材（不然换十次角色就是十几 MB）。
有了角色库之后，keep 列表**必须把库里所有条目的 key 也算进去**，否则切换一次就把库里别的角色的图删了 ——
表现是"库里的角色点开是空的"，而且完全看不出是谁删的。这条有专门的单测盯着。

另外把导入/导出逻辑抽到 `ui/mascotImport.ts` 两边共用（否则迟早出现"从面板导入支持视频、从中心导入不支持"），
并且 `pickFile` 用一个 focus 兜底解决"取消选择不触发 change 导致界面永远在导入中"。

### 3. 桌面小组件：为什么 4×2 是空的

不是坏了，是**排版按固定行数写死的**：

- 固定部分（内边距 + 学期行 + 下一节块 + 分隔线）就占 80dp，而桌面只给 110dp —— 第三行一直被裁到组件外面；
- 更糟的是**拉窄之后**：行内是「时间 + 课程名 + 地点」三列，课程名那列 `weight=1`，宽度不够时被挤成 **0 宽**，
  屏幕上只剩时间和地点 —— 看起来就是"什么都不显示"；
- 选择器里也没有预览图，拖上去之前不知道会显示什么。

改法：判据集中在 `WidgetSize.java`（宽 < 230dp 就收起地点列；行数 = `(高度 − 固定部分) / 行高`），
两个 provider 都实现 `onAppWidgetOptionsChanged`（拉伸即刻重排），4×2 收紧行高让 110dp 放得下两行，
2×2 拉高后补两行；加 `previewLayout` / `previewImage`；应用内画四个尺寸的实时预览。

Web 侧同一套判据在 `src/platform/widgetLayout.ts`（11 个单测），因为**应用里的预览必须与桌面一致**，
否则预览就成了骗人的东西 —— 两个文件的注释互相指着对方，改一边要改另一边。

### 4. 快捷键与拖动改课

**命令表**（`src/app/commands.ts`）：每个动作一条命令（id / 标题 / 分组 / 键位 / enabled / run）。
快捷键说明页**从这张表渲染** —— 手写一份列表，改代码时必然忘记同步，而写了不存在快捷键的帮助页比没有帮助页更糟。
App 的键位处理从硬编码 `if` 改成查表；弹层开着时导航命令 `enabled=false`；输入框里只放行 Esc 与带修饰键的组合。

**拖动改课**：与面板同一条落地路径（写一条 Override），所以自动进撤销栈、自动重排提醒、事后可一键恢复。
三个决定值得记：

1. 手机必须**先长按**才进入拖动 —— 否则横滑翻周会变成"把课拖走"；松手不改动就还是原来的调课面板。
2. 边缘判定按卡高收（`min(18px, 卡高/3)`）：一节的小卡只有 50 多像素高，固定 18px 会让上下两条边缘吃掉整张卡。
3. 预览框用与课程卡**完全相同**的百分比公式定位 —— 预览与结果不一致的拖动，比没有拖动更让人不敢用。

## 十七、分享/公开的功能缺陷，与全站文字截断的排查（v1.9.7）

反馈原文：**「角色分享及公开的功能有问题，同时UI也出现了大量文字因宽度被截断的现象。请严肃优化。」**

### 1. 分享码生成之后看不到它

1.9.6 把生成分享码的入口搬进了「角色中心 → 分享与获取」，但**显示码的那个弹层还挂在 `CloudSheet` 里**：
`cloudShareCurrent` 设了 `cloud.shareSheet`，而 `MascotShareSheet` 只在云弹层打开时才渲染 ——
点完只得到一句「分享码已生成」，码本身在界面上任何地方都不存在。这是典型的"搬了入口没搬出口"。

修法：把 `MascotShareSheet` 提到 App 顶层渲染。并新增 `?open=sharecode` 开发参数，
让探针可以直接量这个弹层（实测：码 `7KQ2M9XF` 在输入框里，两个按钮都在，三档宽度 OVERFLOW 0）。

### 2. 「公开」在新入口里消失，「停止分享」是个死按钮

- 公开开关只在 `MascotCloudSection` 里（云弹层），角色中心没带 → 现在「换一个 → 云端」每行都有，同一接口；
- `cloudUnshareMascot(m)` 要求那一行在当前列表里，`row` 为 undefined 时按钮点了没反应 → 改成按 id 直接停用并返回布尔值。

### 3. 分享码可以被未登录的人列出来（服务端）

用 anon key 直接打线上接口时发现的：

```
GET /rest/v1/mascots?select=id,name,share_code  →  200  [{"name":"黍","share_code":"C8KVFUZ6",…}]
```

码是凭据，能被枚举就等于没有。修法是 `supabase/schema-mascot-share-lock.sql`：

```sql
revoke select on public.mascots from anon;
grant select (id, user_id, name, is_public, path, size_bytes, created_at, updated_at) on public.mascots to anon;
```

**这里踩了一个值得记住的坑**：第一版只写 `revoke select (share_code) …`，跑完看起来"成功了"，
但 anon 依然读得到 —— 因为**表级授权覆盖所有列**，而 `information_schema.column_privileges` 会把表级授权
铺到每一列上显示，看上去像是列级授权。必须撤表级、再按列授回。

实测结果：anon 读其余 8 列 200；带 `share_code` **401**；`resolve_mascot_share` 用真实码仍 200
（下载 4.7MB 对象成功）；`authenticated` 不受影响。

### 4. 文字截断：先量化，再修

「大量文字被截断」这种描述没法直接改代码，先把它变成数字：

- `?clipcheck=1`：遍历 DOM，区分**截断**（overflow hidden / ellipsis / 行数限制真的吃掉了内容）与**溢出但可见**；
- 窄屏探针：Edge 无头窗口最小 504px，量不到 320/360，于是用**精确宽度的 iframe** 装应用跨文档统计，
  并报出"是谁把盒子撑破的"。

第一轮结果（320/360/390）：

| 位置 | 实宽 / 需要 | 症状 |
| --- | --- | --- |
| `.ev-room`（课表卡教室） | 27~33 / 55~61 | 一周 7 天时**每张卡的教室名都被省略号吃掉** |
| `button.preset-card` | 94 / 99 | 一排八张主题卡的名字全被切 |
| `.mascot-slot-name` | 44 / 55 | 「长时间没动」→「长时间…」 |
| `.topbar-row` | 300 / 305 | 学期名被截 |

**同时纠正了两个测量口径的错**（不纠正会一直修错东西）：

1. 「可点区域」是 `::after/::before` 往外扩的绝对定位伪元素，不占布局却计入 `scrollWidth` ——
   扣掉它之后，`icon-btn` 32/38、`week-pill` 36/38 这些"溢出"全部消失（本来就是假阳性）；
2. `OVERFLOW` 原来靠一串选择器豁免横向滚动区，课表主体改成可横滑之后漏了它，一次报出 16 条假溢出；
   改成按样式判断（祖先有 `overflow-x: auto/scroll` 就不算），这才是可持续的写法。

### 5. 结构性的修法

一周 7 天塞进 320px，每列 30 多像素 —— 不是字号问题，是**没有空间**。所以：

- 给课表主体一个最小列宽并允许横向滚动（`--col-min: 62px`）；
- 能横滑时横滑＝看后面的天，不能横滑时横滑＝翻周（原有手势不丢）；翻周也一直能用周次按钮与 ← →；
- 教室/教师名改成两行折行（省略号在这里信息量为零）；预览卡名字、状态格名字、顶栏学期名同理；
- 预览卡色条从写死像素改成百分比（原来第 4 根 99px > 卡宽 94px，被裁掉一角）。

复测：**截断 0 处**，OVERFLOW 0 / SMALL_TAP 0。
